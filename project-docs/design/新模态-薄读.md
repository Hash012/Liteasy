# “薄读” 1agent设计

## 入口
在“模态”的悬浮按钮里增加一个“薄读”的弹出按钮

## 主要依赖的其他模块
“Intuecho社区”（我们待开发的配套社区）
1. 该社区的主要功能是供用户分享阅读文献时的“直觉性的理解”。这些关于自己的理解的字句或图片将与文献唯一的标识（比如doi？或者更好的表征）。可以是针对"全篇"（将只与文献唯一标识关联），也可以针对具体的某一个段落或句子（将不仅与文献唯一标识关联，还要与其中的句段关联）这种理解广义上可以理解为阅读批注，以下简称“共享批注”。
2. 用户可以给其他用户的批注打分。论坛中用户和用户之间存在社会关系。
3. 我们的社区前端是web网页版，而本Liteasy项目主体是一个软件包。应该两者是通过服务器端通信。
4. （此条与什么模态无关）当用户阅读原文献或者在某种阅读模态下时，可以在中间栏进行批注（需要完成批注功能），用户可以选择公开上传批注到社区，针对局部的批注会自动关联到文献的具体句段; 如果不公开上传，批注会随用户批注的对象保存或丢失；用户可以设置为自动上传并公开批注，成为“共享批注”。
5. 当用户读到一篇文献的“整体讲述”时，Liteasy软件将向用户推荐关于所读文献"全篇"的“共享批注”；当用户所关注的局部包含某几个句段时，Liteasy软件将向用户推荐关于涉及到的段落、句子的“共享批注”。推荐的规则基于社区中的“共享批注”与用户的思维语言习惯的契合性，这个契合性通过用户的个人画像、批注发布者的个人画像、对用户语言习惯的建模（比如通过用户发布过的批注、用户评分高的批注）、用户和批注发布者的社会关系的远近等等。


## 页面与交互
1. 作为中间栏的一个新标签页。标签页风格要极简主义，有现代感。（也许可以从中找一些东西来参考：https://github.com/Eneryleen/ai-web-design-codex  https://stitch.withgoogle.com/?pli=1）
2. 在点击“薄读”api来生成后，初状态为对文献全篇的总述。所谓全篇的总述不是一视同仁地概括整个文献，而是针对论文的类别来有重点倾向的概括与呈现，比如：对于理工类实验/推理-结论型的论文，此处只关注：论文中给出的核心结论是什么，以及关键的思路推导和这个结论在学科的知识图谱中的位置（比如：那些是原来已知，那些是本论文揭示的；等等）。此处的类型识别与取舍要非常灵活，核心目的是要让呈现的总述直指“读者一般读完论文后脑子里主要留下的东西”。总述是一段话。占据页面的视觉中心。
3. 根据上面的规则，对于一篇文献，总述中有很大可能不包括这篇文献的某个板块，假如对文献A的总述不包括实验和背景，那么在总述文段下方会有一排悬浮按钮，写着“深入了解实验”“深入了解背景”（按钮上的文字符号是这个意思，具体还需要大胆设计来保证美观），用户可以点击来对这个板块进一步了解（点击后的情况见 下6）
4. 对于总述文字中包括的板块，用户可以用鼠标选中总述中的几句话或者几个词，选中后会弹出“深入了解”的按钮（按钮下有一个输入框，可以补充提示词，也可以不输入直接点击），点击后可以对选中部分或者说选中部分对应的板块进一步了解（点击后的情况见 下6）。对应关系大概是总述中词句和原文词句有映射关系。
5. 中栏核心部分的右边侧会呈现推荐的“共享批注”，推荐的规则见“主要依赖的其他模块的2，5”。“共享批注”推荐栏可以收起，收起成一个位于中间栏右边侧的图标（图标的logo要能表现出“直觉”的含义）
6. 当从上一级的“薄读页面”（比如上述的初状态：“总述”）进入下一级的薄读页面后，将根据选中的范围、深度（相对于初始页面）、补充的提示词来在原标签页内给出针对性的讲述文本（不生成新标签页），从文本中选择词句后可以通过“深入了解”进入下一层。中间栏该标签页的页面上边侧有一个“左/右”箭头，用于回到上一层页面或者回到已经生成的下一层页面（当有多个下一层页面时，鼠标悬停在“右”箭头后或弹出多条下一层的页面的条目，来供用户进一步选择），“共享批注”推荐栏根据规则同步更新。
7. 随着深入了解深度的加深，应该会存在一个深度等价于“文献原文的闭包”，继续深究的话将主要依赖目标文献之外的知识，当用户达到这一深度时应该提醒（比如改变背景色）
8. 虽然是针对局部的讲解，但势必要结合文献的其他部分（局部映射到的原文的其他部分原文）。
9. 呈现的所有文字句段都可以像“主要依赖的其他模块的4”那样批注。
10. 呈现的语言要和系统语言一致（而不是文献原文语言；需要在系统设置里面添加这个设置项，以及每篇文献在进行多模态转换时也要有隐式的目标语言的特征参数，可以通过向ai助手下达指令来设置），默认中文，但关键名词不要翻译（可以采用保留原文名词，括弧号里是意义翻译的形式）。
11. 检索功能如果涉及到身份配置，需要在用户端的设置中留下供用户配置api-key等所需身份信息的输入口。在开发阶段要在工作区建立一个.env文件告诉我写入我的身份配置以供开发中的测试。
12. 论文中的表格、统计图和示意图属于证据的一部分。只有图注、正文复述或可审计的结构化图表证据直接支持时，正文才能讲述对应数字及行列、图例、坐标或视觉关系；从 PDF 文字层偶然提取到若干数字，不等于已经理解图表。若链路只有纯文本投影，必须收缩到该文本直接表达的命题，不能凭数字邻接、版面顺序或模型视觉常识补全图表关系。之后要有真正的图标的解读能力。
13. 推荐功能

## Intuecho 批注闭环实施规则（2026-08-08）

- 广场只有 `annotation`。它必须始终保留至少一个合法文献目标；薄读生成内容目标必须同时保留原文 evidence。
- `reply` 是独立互动记录。纯回复不会成为 annotation；手动关联文献目标的回复会在同一事务生成一条独立 annotation，多个目标仍只对应一条广场内容。两者正文同步更新。
- 父 annotation 删除后，回复投影不再显示；派生 annotation 不删除，详情只投影“原回复对象已删除”，不复制已删除父正文。
- annotation 采用 1–5 星整数评分。每用户每 annotation 只有一个当前评分，允许改分，禁止自评；纯 reply 不评分。
- 机构只有名称，学段由用户填写。发布和每次编辑刷新展示快照，版本表保留旧内容、目标、标签和快照审计。
- 组织可见内容绑定发布时指定的一个组织。作者离开后仍可查看和删除自己的内容，但不能编辑或向该组织新增；当前成员可见，组织管理员保留治理权。
- 组织 owner/admin 的撤回与恢复必须实时调用 Liteasy 组织权限服务授权并写追加写审计，不接受客户端自报角色。账号注销时删除非公开正文及其编辑历史；公开正文和历史保留但去除作者身份，治理审计保留原批注 ID。
- 论坛个人区提供“组织批注”视图：Intuecho 以服务身份查询当前用户的组织清单并分组读取，普通成员不看到撤回项，owner/admin 可填写原因撤回或恢复；用户 token 不转交 Liteasy。
- `/A` 在权限、机构、文献等硬过滤后执行本次请求的本地语义二元分类，再把命中候选交给推荐排序；结果不保存为标签。
- Liteasy 自动公开在创建、编辑或开启公开时立即尝试后台同步；失败结果写回文档中的持久待重试状态。手动“立即同步”仅作为恢复操作，不再是自动公开的必要步骤。
- Liteasy 直接调用推荐 API。推荐项可在软件内展开正文，并链接到 `/annotations/:id` Web 详情；复杂多文献编辑继续使用五分钟一次性交接单。

本机开发验收已覆盖桌面会话同步、推荐回读、Web 交接恢复、纯回复、带证据回复派生、改分、自评拒绝、删除父批注后的派生详情，以及组织管理员在 Web 查看撤回项并填写原因恢复。该证据只说明本机开发闭环，不代表生产部署、真实 MFA、托管 PostgreSQL 或正式域名已经完成。

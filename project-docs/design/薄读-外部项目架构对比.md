# 薄读外部项目架构对比与技术演进建议

## 资料范围

本文比较以下五个参考项目与 LiteasyClaw 当前“薄读”模态的架构和实现差异：

- OpenDraft: <https://github.com/federicodeponte/opendraft>，本地浅克隆版本 `93fa13c`。
- Open Paper: <https://github.com/khoj-ai/openpaper>，本地浅克隆版本 `2ec9807`。
- Literature-Review-Assistant: <https://github.com/PrajjwalLyzr/Literature-Review-Assistant>，本地浅克隆版本 `0058a1d`。
- papers2dataset: <https://github.com/eamag/papers2dataset>，本地浅克隆版本 `cd13e3a`。
- SynapseFlow: <https://github.com/mrkingsleyobi/synapseflow>，本地浅克隆版本 `f80591e`。
- LiteasyClaw 薄读现状：`LiteasyClaw/desktop/src/app/features/thin-reading/`，以及多模态产物入口 `LiteasyClaw/desktop/src/app/features/artifacts/`。

比较重点不是 UI 相似度，而是论文阅读、证据链、异步任务、结构化产物、可恢复流水线、评测和可迁移工程模式。

## 一句话结论

OpenDraft 是“长文稿生成引擎”，优势在可复现多阶段 Agent 流水线、引文校验、checkpoint、导出和质量门。Open Paper 是“研究阅读产品”，优势在完整 Web 产品栈、PDF 阅读器、批注、对话、项目、证据引用、异步任务和评测。Literature-Review-Assistant 是“单 PDF 快速综述 Demo”，优势在实现简单、固定问题模板清晰、接入成本低。papers2dataset 是“文献到结构化数据集工具”，优势在 OpenAlex 检索、PDF 下载、BFS 引文图扩展、结构化抽取和 Agent Skill 化。SynapseFlow 是“多 Agent 研究发现系统”，优势在 MCP/多服务/图谱/向量检索的目标架构，但当前源码中部分能力更像依赖封装和产品蓝图，需要谨慎评估成熟度。

LiteasyClaw 的薄读已经跨过本地模板 MVP：root 与 branch 均走 live-only Agent 链路，已有论文类型 prompt registry、句级 evidence ID、PDF evidence span 与 quote 高亮、claim 状态、OpenAlex 外部来源白名单和有界一跳关系、artifact 隔离的外部检索失败恢复与完成结果复用、层级导航、全正文选区、批注/pending_public 和确定性 eval harness。当前主要差距转为真实 PDF gold set、多 provider 外检索、PDF offset 级定位、Intuecho 后端与 live-model nightly eval。

## 持续对比机制

本文不是一次性竞品摘要。每次强化薄读前后，应执行以下流程：

1. 记录五个参考仓库的 commit，不以 README 宣称替代源码证据。
2. 按工作流、检索、证据、prompt、失败恢复、评测六个维度检查新增能力。
3. 每个候选设计标记为 `已采纳`、`待采纳`、`不采纳`，并写明 Liteasy 的对应代码和理由。
4. 只吸收机制与约束，不复制受许可证保护的实现、提示词或视觉代码。
5. 对“多 Agent 数量、性能、覆盖率”等宣传性指标，必须在源码和测试中找到可验证实现后才作为依据。

### 本轮由对比驱动的改进

- OpenDraft 的“生成后质量门”被改造成薄读专属 trace gate，不采用其以字数和 citation density 为主的长文评分。
- Open Paper 的“每个事实单元独立 citation”被落实为 live 输出必须显式提供 `summarySentences`；本地 parser 不再在 live 路径中猜测句级来源。
- papers2dataset 的明确失败状态被落实为：质量门第一次失败进入 `repairing_structured_output`，第二次失败明确终止，并把首次失败原因保存在 `thinReading.qualityGate`。
- papers2dataset 的 cited/citing/related 区分被改造成适合交互阅读的有界一跳关系：使用本轮 OpenAlex work 的 `referenced_works` / `related_works`；目标不在搜索页时可按 DOI 或 arXiv ID 精确补取一次目标 work，仍不运行无界 BFS。没有图关系的 `topic_search` 还需通过确定性最低词汇相关性门。
- 修复 prompt 把上一轮输出放入无指令效力的数据边界，避免模型输出中的文字被当作新指令；修复只能使用原 evidence/source 白名单。
- 中文术语要求从泛化语言偏好提升为可评测约束：首次实质使用必须写成“原文术语（准确中文释义）”；live gold case 会同时检查原词和释义，避免仅中文翻译或不稳定的字面直译。
- Literature-Review-Assistant 的固定问题链被提炼为不展示给用户的 coverage audit：experimental、systems、dataset、survey、humanities 等类型各自检查高价值阅读维度；模型只能保留改变读者认知模型的已证实维度，重要但未覆盖者生成遗漏入口，禁止输出固定大纲。

## OpenDraft 架构与实现

### 定位

OpenDraft 是一个面向长篇学术草稿生成的 Python 引擎。README 将其定位为从 prompt 到 source-grounded draft 的自动研究引擎，强调多 Agent、真实学术来源、引文校验和 PDF/DOCX/LaTeX 导出。

它不是阅读器，也不是交互式批注产品。它的强项是把“生成一篇研究草稿”拆成可审计流水线。

### 模块结构

关键目录和文件：

- `engine/draft_generator.py`: 顶层 orchestrator，负责串联 Research -> Structure -> Citations -> Compose -> Validate -> Compile/Export。
- `engine/phases/`: 阶段拆分，包括 `research.py`、`structure.py`、`citations.py`、`compose.py`、`validate.py`、`compile.py`。
- `engine/prompts/`: 分阶段 prompt，按 `01_research`、`02_structure`、`03_compose`、`04_validate`、`05_refine`、`06_enhance` 组织。
- `engine/utils/api_citations/`: Semantic Scholar、CrossRef、OpenAlex、Serper、Gemini grounded search 等引文来源适配。
- `engine/utils/checkpoint.py`: checkpoint。
- `engine/utils/quality_gate.py`: 质量门。
- `engine/utils/citation_compiler.py`、`citation_database.py`、`factcheck_verifier.py`: 引文编译、引文库和事实核验。
- `engine/utils/export_professional.py` 与 `pdf_engines/`: PDF/DOCX/Markdown/LaTeX 导出。

### 流水线设计

OpenDraft 的 `docs/ARCHITECTURE.md` 明确分为：

1. Research: Scout、Deep Research、Scribe、Signal，发现和分析论文。
2. Structure: Architect、Formatter，设计论文结构。
3. Citation Management: 非 LLM 确定性处理，引文去重、元数据补全、生成 citation database。
4. Compose: Crafter 分章节写作。
5. QA: Thread、Narrator、FactCheck 等报告。
6. Compile & Export: 组装、引文编译、摘要、后处理、导出。

这套架构的价值在于：LLM 负责语义工作，确定性代码负责状态、校验、去重、编译和导出。每个阶段都有清晰输入输出，方便断点恢复和测试。

### 对薄读的优势

OpenDraft 相比当前薄读有这些明显优势：

- 有真正的多阶段内容生成，而不是本地模板生成。
- 有引文和来源校验，不只显示“看起来像证据”的文字。
- 有可恢复输出目录和 checkpoint，长任务失败后可以续跑。
- 有质量门和大量回归测试，能防止生成质量退化。
- prompt 被分阶段文件化，便于单独调试和版本管理。
- 支持多语言章节名和输出格式，语言能力比当前薄读的 `zh/en` 简单分支更系统。

### 对薄读的限制

OpenDraft 也不适合直接复制成薄读：

- 它是“生成最终文稿”的批处理引擎，不是高频交互阅读 UI。
- 它以主题和文献检索为起点，不以用户正在阅读的 PDF 选区为中心。
- 它生成较重，典型运行时间和成本都高于薄读的交互预期。
- 它不提供 PDF 原文定位、局部选区映射、批注和右侧推荐栏这样的阅读产品能力。

对 Liteasy 来说，OpenDraft 更适合作为“薄读生成引擎的工程模式参考”，不是 UI 或产品流的直接参考。

## Open Paper 架构与实现

### 定位

Open Paper 是完整研究阅读工作区。README 中的能力覆盖 PDF 上传、AI brief、starter questions、逐段 citation、点击跳回原文、highlight、annotation、notes、项目、多论文问答、数据表、OpenAlex/开放文献发现、Zotero 导入、音频概览。

它与薄读目标最接近，因为二者都围绕“正在读论文”而不是“写一篇论文”。

### 服务架构

Open Paper 是典型三服务架构：

- `client/`: Next.js 15 + React 19 + TypeScript 前端。
- `server/`: FastAPI 后端，Postgres/SQLAlchemy/Alembic，负责 API、认证、数据库、项目、批注、对话、搜索、订阅、Zotero、LLM 编排。
- `jobs/`: Celery worker + FastAPI jobs API，负责 PDF 解析、Zotero 同步、数据表、音频等异步任务。

开发文档要求本地同时运行：

- client: `3000`
- server: `8000`
- jobs API: `8001`
- RabbitMQ/Redis: `5672` / `6379`
- Flower: `5555`

### 前端结构

`client/src/components/` 里有大量产品化组件：

- `PdfHighlighterViewer.tsx`
- `Annotation.tsx`
- `InlineAnnotationMenu.tsx`
- `ConversationView.tsx`
- `MentionInput.tsx`
- `ProjectWorkspaceProvider.tsx`
- `DataTableGenerationView.tsx`
- `AudioOverview*`
- `Zotero*`

这说明 Open Paper 的阅读体验不是单独一个 Tab，而是围绕 PDF、highlight、annotation、chat、project 构成完整操作面。

### 后端 API 和 LLM 层

`server/app/main.py` 注册了大量 router：

- paper、upload、image、audio、tag
- conversation、message
- highlight、annotation
- projects、project papers、project conversations、project artifacts、project tables
- search local/global、discover
- Zotero、webhook、subscription

LLM 层在 `server/app/llm/`：

- `paper_operations.py`: 单论文问答和 narrative summary。
- `multi_paper_operations.py`: 多论文问答，继承 evidence gathering。
- `evidence_operations.py`: 多轮工具调用式证据收集、压缩、citation artifact、引用解析。
- `tools/file_tools.py`: read/search/view/read_abstract/search_all_files 等工具。
- `citation_handler.py`、`citation_agent.py`: citation 解析和查找。

`EvidenceOperations.gather_evidence` 的工程重点是：先从用户可访问论文中构造候选 paper options，再允许 LLM 多轮调用 read/search/view/find_citation 等工具，收集 evidence collection；当工具结果过大时先压缩，再进入回答阶段。这个设计比“把所有片段拼进 prompt”更适合真实阅读场景。

### jobs 异步层

`jobs/src/tasks.py` 里有 `upload_and_process_file` 和 `process_data_table` 等 Celery task。PDF 处理流程大致是：

1. 从 S3 下载 PDF。
2. 提取文本、图片、页面 offset。
3. 并行生成 preview 和 LLM 元数据。
4. 将结果通过 webhook 回传 server。

`jobs/src/pdf_processor.py` 里还做了可处理 PDF 的边界控制：

- 过少文本视为扫描或解析失败。
- 过大文本根据模型上下文窗口限制截断。
- 如果截断会丢掉过多内容，则拒绝处理，避免生成不可信元数据。

这类输入质量控制是当前薄读缺失的。

### 评测

`server/evals/README.md` 描述了 ResearchQA 评测套件，指标包括 factual accuracy、completeness、groundedness、citation precision、citation recall、citation accuracy 和 latency。它能比较完整 harness 与 raw PDF baseline。

这对薄读非常关键：薄读不是普通摘要，质量问题很隐蔽。如果没有评测，很容易出现“文本顺滑但证据错位”的退化。

### 对薄读的优势

Open Paper 相比当前薄读的优势最大：

- 有真实 PDF 阅读器、highlight、annotation、notes。
- 有选区/引用跳回原文的产品闭环。
- 有多论文和项目级知识组织。
- 有异步 PDF 解析、S3、数据库、webhook、状态回传。
- 有证据收集工具调用，而不是模板化摘要。
- 有 ResearchQA 评测套件，能量化 groundedness 和 citation。
- 有 Zotero 导入，适合真实研究者已有库迁移。

### 对薄读的限制

Open Paper 也有不适合直接迁移的地方：

- AGPL-3.0 许可证要求强，Liteasy 不应直接复制代码，除非接受许可证约束。
- 它是 Web/SaaS 优先，本地桌面和 Liteasy 的 Tauri 架构不同。
- 它的基础设施很重：Postgres、S3、Celery、RabbitMQ/Redis，对本地桌面应用门槛高。
- 它的交互核心是 PDF + Chat，薄读需要的是“层层压缩/展开”的阅读路径，数据模型应更像一棵可导航的语义树。

对 Liteasy 来说，Open Paper 最值得借鉴的是“PDF 选区、证据映射、批注、异步任务和评测”，不是完整后端照搬。

## Literature-Review-Assistant 架构与实现

### 定位

Literature-Review-Assistant 是一个非常轻量的 Streamlit 应用，用 Lyzr 的 `QABot.pdf_qa` 对用户上传的单个 PDF 做固定问题回答。它更像一个“论文综述 Demo”，不是完整研究工作台，也不是多阶段 Agent 流水线。

### 模块结构

仓库结构很小：

- `app.py`: Streamlit 页面、文件上传、调用 reviewer、展示结果。
- `utils/utils.py`: 文件保存、清空上传目录、固定 prompt 列表、循环调用 `agent.query`。
- `requirements.txt`: 依赖包含 Streamlit、Lyzr、OpenAI、LlamaIndex、LangChain、Weaviate 等。

### 实现流程

核心流程是：

1. 用户上传 PDF。
2. `save_uploaded_file` 清空 `data/` 目录并保存新文件。
3. `literature_review` 取目录中的第一个文件，调用 `QABot.pdf_qa(input_files=[Path(path)])`。
4. `reviewer` 按固定 prompt 顺序调用：
   - Summary
   - Research Objectives
   - Methodology
   - Findings and Results
   - Discussion and Conclusions
   - Related Research
   - Prototype
5. Streamlit 逐段展示回答。

### 架构特点

这个项目的价值在“极简”：

- 几乎没有自研后端。
- 没有复杂状态管理。
- 没有 artifact 模型。
- 没有异步任务。
- 没有引用校验。
- 没有 PDF 页面级选区映射。
- 主要能力交给 Lyzr QABot 黑盒。

从工程角度看，它的质量上限受限于 Lyzr 框架和固定 prompt。它适合快速验证“用户上传论文后得到若干固定综述栏目”的需求，但不适合支撑薄读这种可层层深入、可追踪证据、可批注、可推荐的产品形态。

### 对薄读的优势

它相对当前薄读的直接优势是把完整 PDF 的检索与问答封装在一个黑盒服务内。Liteasy 薄读也从本地导入的 PDF 全文 chunk 中检索真实 evidence，并拒绝在没有可引用文本时生成；其差距是没有同等的多轮 read/search/view 工具循环和服务端全文索引。不能仅凭“完整 PDF RAG”这一宣传把黑盒回答视为更可靠的证据链。

另一个可借鉴点是固定栏目 prompt：

- Summary
- Objectives
- Methodology
- Findings
- Discussion
- Related Research
- Prototype

薄读 root generation 可以借鉴这个思路，但不能照搬为最终 UI。更合适的做法是把这些固定栏目变成内部 planner 的候选视角，而不是把七个栏目直接展示给用户。

### 对薄读的限制

- 单 PDF、单用户、单会话，不能处理文献集。
- 固定 prompt 顺序，没有动态论文类型识别。
- 没有 evidence span、claim、citation、page jump。
- 没有可恢复生成状态。
- 没有测试。
- 上传目录每次清空，只适合 Demo。
- `requirements.txt` 文件疑似带 NUL/编码异常，工程维护质量一般。

对 Liteasy 来说，这个项目只适合作为“固定问题链可作为 planner 覆盖检查”的提醒；不能把它的固定栏目或黑盒 QA 当作薄读的正文生成和证据验证方案。

## papers2dataset 架构与实现

### 定位

papers2dataset 是从开放论文中批量抽取结构化数据集的工具。README 将它描述为 AI agents 读取 papers 并创建 dataset，核心场景是数据只存在于论文文本里，需要自动搜索、下载、筛选、抽取，并输出 CSV 或发布到 HuggingFace。

它不是阅读产品，也不是自然语言问答产品。它的强项是“文献发现和批量结构化抽取”。

### CLI 流程

`papers2dataset/__main__.py` 提供命令：

- `create`: 根据用户描述生成项目资产。
- `search`: 用 OpenAlex 查询并下载初始 PDF。
- `extract`: 并发处理队列中的论文。
- `export`: 合并 JSON 为 CSV，并可发布 HuggingFace。
- `vibe`: create -> search -> extract -> export 一键全流程。

### 项目资产

Skill 文档和 workflow 文档规定每个项目目录包含：

- `schema.json`: 数据抽取 JSON Schema。
- `prompt.txt`: PDF 抽取指令。
- `relevance_prompt.txt`: 相关性判断指令。
- `search_query.txt`: OpenAlex 检索词。
- `bfs_queue.json`: BFS 队列状态。
- `pdfs/`: 下载的 PDF。
- `data/`: 抽取的 JSON。

这个设计的优点是把“任务定义”和“执行代码”分离。用户可以审查 schema、prompt、query，再启动自动流程。

### OpenAlex 和 BFS 引文图

`openalex_client.py` 封装：

- `search_works`
- `fetch_work`
- `fetch_cited_works`
- `fetch_citing_works`
- `fetch_related_works`
- PDF 下载逻辑

`bfs_queue.py` 用 JSON 存 queue、processed、skipped、failed，实现停止/恢复。

`extractor.py` 中 `process_one_paper` 的流程是：

1. 拉取 OpenAlex metadata。
2. 下载 PDF。
3. 用 LLM 判断相关性。
4. 用 LLM 按 schema 从 PDF 抽取结构化 JSON。
5. 拉取 related/cited/citing papers，加入队列。
6. 标记 processed/skipped/failed。

### 模型路由

`models.py` 使用 LiteLLM Router：

- relevance checker 默认走一个开放模型。
- data extractor 和 project generator 默认走 Gemini。
- 配置 fallback models。
- 用 `response_format` 和 schema 约束 JSON 输出。

### 对薄读的优势

papers2dataset 对当前薄读的优势不在 UI，而在“外延阅读”和“结构化约束”：

- 能从一篇论文扩展到 cited/citing/related works。
- 队列状态简单但有效，可停可续。
- 抽取产物由 schema 约束，便于后续检索、筛选和评测。
- 失败状态明确区分 no_pdf、not relevant、extraction error。
- Agent Skill 化让它可以嵌入不同 Agent 环境。

### 对薄读的限制

它也不适合直接替代薄读：

- 没有阅读 UI。
- 没有原文选区互动。
- 没有批注和推荐体验。
- README 明确 TODO 里还有去重、PDF 下载增强、调度改进和测试。
- 它适合离线批量处理，不适合薄读的实时逐层深入。

对 Liteasy 来说，papers2dataset 最值得借鉴的是“引文图扩展、schema 约束和 BFS 队列”，尤其适合薄读达到“文献闭包”之后继续向外部知识扩展。

## SynapseFlow 架构与实现

### 定位

SynapseFlow README 将其描述为多 Agent 研究自动化系统，目标是跨域文献综述、引文分析、假设生成和实时图谱可视化。它的方向和薄读的“文献外延/知识图谱”部分相关，但它不是论文阅读器，也没有 PDF 选区和批注。

需要注意：README 宣称 66 agents、213 MCP tools、1000+ papers/minute、95% coverage。源码中能看到这些数字被写入配置、health/stats 和 MCP handler，但许多具体能力由外部依赖包承接，或以 placeholder 工具生成。评估时应把它视为“目标架构和集成示例”，而不是完全自包含、已验证的成熟研究系统。

### 服务架构

SynapseFlow 是 TypeScript monorepo：

- `synapseflow/frontend`: Next.js + React + Tailwind + D3。
- `synapseflow/backend`: Fastify API server。
- `synapseflow/mcp-server`: MCP stdio/SSE server。
- `synapseflow/docker-compose.yml`: frontend、backend、mcp-server、Postgres/pgvector、Redis、Neo4j、AgentDB volume。

根 `package.json` 使用 npm workspaces 管理 `frontend`、`backend`、`mcp-server`。

### 后端编排

`backend/src/index.ts`：

- 初始化 Fastify。
- 注册 CORS 和 rate limit。
- 创建 `ResearchOrchestrator`。
- 注册 `/api/research`、`/api/search`、`/api/embeddings`、`/api/stats`。
- `/health` 返回 agent 和 database 状态。

`ResearchOrchestrator.ts` 封装：

- `ClaudeFlow`
- `AgenticFlow`
- `AgentDB`
- `RuvSwarm`
- `StrangeLoops`
- `SublinearToolkit`
- `HfInference`

主流程 `research(query)`：

1. 调用 `claudeFlow.orchestrate` 生成 workflow。
2. 并行运行 PaperScraperAgent、CrossDomainAgent、TrendAnalysisAgent。
3. 用 ruv-swarm 批处理 papers，生成 embedding、summary、NER 等。
4. 写入 AgentDB。
5. 用 sublinear-toolkit 构建 citation graph 和 PageRank。
6. 用 HuggingFace text generation 生成 hypotheses。
7. 写入 reflexion memory。

### MCP 层

`mcp-server/src/mcp-handler.ts` 负责：

- 连接 backend API。
- 初始化 MCP tool 列表。
- 暴露 `executeResearch`、`getStats`、`getHealth`。

这里的 213 个工具主要由 `generateTools` 批量生成 placeholder 名称，并混入少量具名 agent 工具。因此它的 MCP 层展示了“如何把研究系统暴露给 Agent/MCP”的外壳，但并没有在仓库内逐个实现 213 个真实工具。

### 前端图谱

`frontend/components/CitationGraph.tsx` 使用 D3 force simulation：

- papers -> nodes。
- citationGraph -> PageRank 或 links。
- zoom/pan/drag。
- tooltip。
- hover 高亮相邻节点。
- 节点颜色按 domain。

这对 Liteasy 的“薄读外部知识扩展”和“文献关系图”有参考价值。薄读本身不应该变成图谱界面，但当用户离开目标论文闭包、进入相关文献时，右侧或独立 artifact 可以用图谱解释外部证据来源。

### 对薄读的优势

SynapseFlow 相对当前薄读的优势在系统方向：

- 有研究 query -> paper discovery -> graph -> hypothesis 的端到端框架。
- 有 Zod schema 约束 API 输入输出。
- 有 MCP/SSE 思路，可把研究动作暴露给外部 Agent。
- 有 D3 citation graph，可视化文献关系。
- 有向量库、图数据库、缓存、MCP server 的部署草图。

### 对薄读的限制

- 没有 PDF 阅读器和原文选区。
- 没有薄读式节点树。
- 没有 evidence span 和点击回原文。
- 数据库初始化在源码里仍是注释/占位。
- MCP tools 大量是生成的 placeholder。
- 研究能力强依赖外部包，仓库自身逻辑较薄。
- 不适合直接移植到 Tauri 桌面端。

对 Liteasy 来说，SynapseFlow 最适合作为 Phase 6 之后的参考：当薄读需要跨论文、跨域、外部文献图谱和 Agent tool 暴露时，它的形态有借鉴意义。但它不能解决当前薄读最核心的“读当前 PDF 是否读准”的问题。

## LiteasyClaw 薄读当前实现

### 当前数据模型

`thinReading.types.ts` 定义了薄读的核心结构：

- `ThinReadingNodeSource`: `root_overview`、`omitted_section`、`selected_text`。
- `ThinReadingRecommendationScope`: `whole_paper`、`section`、`selected_passage`。
- `ThinReadingNode`: 节点 ID、父子关系、depth、source、summary、omittedSections、recommendations、withinPaperClosure。
- `ThinReadingDocument`: artifact ID、paper IDs、title、target language、active node、nodes map、root node、version。

这个模型是薄读当前最好的资产：它天然支持树状深入、同一 Tab 内导航、局部来源和推荐范围。

### 当前生成逻辑

`thinReadingProjection.ts` 当前做了：

- 固定遗漏板块定义：实验、消融、数据集、局限、索引代价，以及英文标签。
- 根据 `targetLanguage` 粗略选择中文或英文。
- 将导入的 retrieval chunks 规整、排序、拼入根 summary。
- 生成 root node。
- 对遗漏板块或正文选区生成本地 draft。
- `advanceThinReadingDocument` 生成 child node。
- child ID 由 artifact、parent、source 的稳定 hash 生成，重复点击会跳转到已有节点。

这套 projection 只负责确定性节点树与重复分支复用；实际 root/branch 由 live-only Agent 生成。模型输出必须通过 JSON Schema、Zod、evidence/source 白名单和句级 trace gate，summary sentence 也会持久化映射到 PDF evidence span。它仍缺少 artifact 级可恢复 checkpoint，不能把正在运行的模型调用在应用重启后续跑。

### 当前 UI 逻辑

`ThinReadingTab.tsx` 当前提供：

- 顶栏标题、源文、语言、左右箭头。
- root / depth breadcrumb。
- 主体 summary。
- 遗漏板块按钮。
- 鼠标选中 summary 文本后弹出深入输入框。
- 多个已生成下一层时，右箭头弹出分支菜单。
- Intuecho 侧栏展示 recommendation。

这已经符合设计文档中“同一标签页内逐层深入”的基本交互。

### 当前工作流

`useArtifactActions.ts` 中 `thin_reading` 的特殊处理：

- 如果选中文献已经导入，创建 artifact task。
- 为 root 创建稳定 `artifactId` 和单篇 `ThinReadingGenerationContext`，然后调用 `runAgentAnalysis`。
- 通过 Agent 进度事件显示解析、规划、证据检索、生成、修复、验证和保存阶段。
- 仅在解析并通过质量门后调用 `createThinReadingDocument`，并用 `artifactResultClient.save` 原子保存结果。
- branch 复用同一 artifact，继承父层 claim/evidence；完成后更新并持久化薄读文档。

也就是说，薄读已是 Agent 持久化分析产物；尚未持久化的是运行中 checkpoint 和可跨重启恢复的未完成任务。

## 参考项目相对薄读的主要优势

### 1. 真实证据链

当前薄读已有 `ThinReadingEvidenceSpan`、claim、句级映射和 PDF quote 高亮；`recommendationScope` 还保留 whole-paper / section / selected-passage 的身份与证据范围。Open Paper 的差距在于多轮工具式证据收集、压缩前后 citation sidecar 和服务器端项目级索引；OpenDraft 的差距在于 citation database、factcheck 和可恢复 checkpoint。Literature-Review-Assistant 的完整 PDF QA 是黑盒能力，不能据此推断其证据可定位性高于 Liteasy。

薄读下一步应强化：

- PDF glyph/字符坐标或 OCR 后 offset，提升扫描件与复杂文本层的稳定定位。
- 压缩前后 citation sidecar，保留 evidence 筛选和摘要压缩过程中的可审计映射。
- 多轮 read/search/view 工具循环，在大论文中按需读取而非只依赖初始检索窗口。

### 2. 异步任务和可恢复性

Open Paper 用 Celery 跑 PDF/表格/音频任务，OpenDraft 有 checkpoint，papers2dataset 有 BFS queue。SynapseFlow 通过多服务和 MCP/SSE 展示了长任务状态和外部 Agent 入口的目标形态。当前薄读已有真实 Agent 阶段、取消和完成产物持久化，但运行中 task 仍只存在内存，应用重启后不能续跑未完成调用。

成熟薄读应有：

- `queued -> parsing -> planning -> generating_root -> validating -> saving -> completed` 状态。
- branch generation 单独成为可取消任务。
- 每个 node 生成后即时持久化。
- 失败时保留已有节点，而不是整个 artifact 丢失。

### 3. 结构化输出约束

papers2dataset 用 JSON Schema 约束抽取结果，OpenDraft 用 Pydantic model 保护 LLM JSON parse，SynapseFlow 用 Zod 约束 API 输入和前端数据。当前薄读已将对应 Zod contract 传给 provider，并在客户端做严格 schema、evidence/source 白名单和 trace gate；差距是把契约、prompt 和 eval fixture 进一步版本化为可独立审查的任务资产。

薄读需要：

- Zod schema 或共享 JSON Schema 校验 `ThinReadingDocument` 和 `ThinReadingNodeDraft`。
- LLM 输出必须是结构化 JSON，不要从 Markdown 中解析。
- 校验失败时进入 retry / fallback / degraded mode。

### 4. 评测闭环

Open Paper 有 ResearchQA，OpenDraft 有大量质量/引文/事实核验测试，SynapseFlow 至少配置了 backend/frontend/e2e 测试框架。当前薄读已有 deterministic eval、真实 PDF-backed gold cases、OpenAlex 图关系和可选 live-model eval，能证明部分证据与结构契约；仍没有覆盖 5-20 篇跨学科真实模型样本的质量基线，也没有浏览器级人工响应式验收。Literature-Review-Assistant 和 papers2dataset 在测试方面参考价值较弱。

薄读应建立小型评测集：

- 固定 10-20 篇论文 PDF。
- 每篇手写 gold summary、关键遗漏板块、选区深入答案、引用位置。
- 指标包括：coverage、groundedness、citation precision、branch relevance、language consistency、hallucination rate。

### 5. 阅读产品完整度

Open Paper 的 PDF highlighter、annotation、notes、chat side-by-side 是薄读成熟的必要上下游。当前薄读已可从句级 evidence marker 跳到 PDF 文本层并高亮 quote，生成文本、外部来源和推荐线索都可批注；其缺口是扫描 PDF 的 OCR / 稳定坐标、原生 PDF 选区直接发起薄读分支，以及真实 Intuecho 社区同步。

薄读要到设计文档目标，必须接入：

- PDF 原文选区。
- 薄读文本选区和原文句段映射。
- 用户批注。
- 批注公开/私有状态。
- Intuecho 推荐 API。

### 6. 固定综述视角

Literature-Review-Assistant 的固定 prompt 列表虽然产品形态简单，但能提醒薄读 root planner：对多数论文，用户通常关心 objectives、methodology、findings、discussion、limitations、related research 等稳定问题。薄读不应把这些栏目机械展示出来，但可以把它们作为内部候选视角，再由论文类型识别决定哪些进入总述、哪些成为 omitted section。

### 7. 文献外延能力

papers2dataset 的 OpenAlex + cited/citing/related works，以及 SynapseFlow 的 citation graph 方向，都能解决薄读设计中的“达到文献闭包后继续深究”。当前已用 `inside_paper / near_boundary / outside_paper` 表达闭包状态，并由父层状态、显式外部意图、深度和本轮结构化外部来源决定是否检索与越界；它仍是保守的启发式策略，尚非可学习或可配置的完整闭包估计器。

薄读可借鉴：

- 当前 node 的 evidence coverage 是否已覆盖目标文献内部。
- 超出内部证据时提示“将进入外部知识扩展”。
- 使用 OpenAlex DOI / title / authors 匹配相关文献。
- 把外部扩展作为单独 branch 类型，而不是混入论文内解释。

## 薄读自身已经优于参考项目的点

当前薄读已形成一条可用的证据驱动阅读路径，并有这些产品抽象：

- `ThinReadingDocument` 节点树比普通 chat history 更适合“层层深入”。
- `source.kind` 明确区分 root、遗漏板块、正文选区，符合薄读独特交互。
- `activeNodeId` + `childIds` 让同一 Tab 内导航简单。
- `closureState` 区分论文内、接近边界和论文外，并驱动外部来源视觉状态。
- `recommendationScope` 保存 Intuecho 推荐的 paper identity、section 或选区 evidence 范围。
- React UI 已实现总述、遗漏入口、选区深入、分支菜单、祖先路径、左右导航、证据 marker 和本地批注队列。

因此薄读不应该改成 Open Paper 的普通 chat，也不应该改成 OpenDraft 的长文稿流水线。正确方向是保留薄读节点树交互，把底层生成和证据链补齐。

## 建议的成熟薄读目标架构

### 分层

建议保持仓库现有依赖方向：`layout -> controllers -> features -> shared types / clients`。薄读目标架构可拆为：

1. `features/thin-reading`
   - 只保留薄读领域类型、UI、projection、schema、局部交互。
   - 不直接依赖 `layout` 或 `AppShell`。

2. `features/artifacts`
   - 继续负责多模态入口、任务列表、artifact tab、catalog。
   - 不承载薄读生成细节。

3. `controllers` 或 artifact workflow controller
   - 编排薄读任务状态、取消、进度、保存。
   - 将 UI 操作转换为 thin-reading generation request。

4. `services/dev-cloud` 或 Agent runtime
   - 负责真实 PDF/RAG/LLM 薄读生成。
   - 提供 root generation、branch generation、evidence mapping、recommendation stub/API。

5. 持久化层
   - 本地 catalog 缓存打开状态。
   - 完整薄读产物保存为 versioned JSON。
   - node 级别可增量保存。

### 核心数据结构建议

在当前类型基础上扩展：

```ts
export type ThinReadingEvidenceSpan = {
  id: string;
  paperId: string;
  chunkId?: string;
  page?: number;
  quote: string;
  normalizedQuote?: string;
  textStart?: number;
  textEnd?: number;
  confidence: number;
};

export type ThinReadingClaim = {
  id: string;
  text: string;
  evidenceIds: string[];
  status: "grounded" | "weak" | "unsupported";
};

export type ThinReadingGenerationStatus =
  | "draft"
  | "generating"
  | "verified"
  | "needs_review"
  | "failed";
```

节点扩展：

```ts
export type ThinReadingNode = {
  // existing fields...
  claims?: readonly ThinReadingClaim[];
  evidence?: readonly ThinReadingEvidenceSpan[];
  generationStatus?: ThinReadingGenerationStatus;
  closureBoundary?: {
    state: "inside_paper" | "near_boundary" | "outside_paper";
    reason: string;
  };
};
```

### 生成 API 建议

Root generation:

```ts
type CreateThinReadingRootRequest = {
  artifactId: string;
  papers: Array<{ id: string; title: string; doi?: string }>;
  targetLanguage: string;
  chunks: Array<{
    id: string;
    paperId: string;
    page?: number;
    text: string;
  }>;
};
```

Root response:

```ts
type CreateThinReadingRootResponse = {
  node: ThinReadingNode;
  omittedSections: ThinReadingSectionToken[];
  evidence: ThinReadingEvidenceSpan[];
  claims: ThinReadingClaim[];
  diagnostics: {
    paperType: string;
    coverage: number;
    warnings: string[];
  };
};
```

Branch generation:

```ts
type CreateThinReadingBranchRequest = {
  document: ThinReadingDocument;
  parentNodeId: string;
  source:
    | { kind: "omitted_section"; sectionKey: string; label: string }
    | { kind: "selected_text"; excerpt: string; prompt?: string; evidenceIds?: string[] };
};
```

### 生成流水线建议

借鉴 OpenDraft 的阶段拆分，但保持薄读轻量：

1. `prepare_context`
   - 收集 selected papers、retrieval chunks、PDF page offsets、metadata。
   - 校验文献已导入。

2. `classify_paper`
   - 判断论文类型：实验型、理论型、系统型、综述型、数据集型等。
   - 决定总述关注点。

3. `plan_thin_reading`
   - 生成 root summary 计划。
   - 生成 omitted sections。
   - 生成 evidence query plan。

4. `retrieve_evidence`
   - 从本地 chunks/PDF text 检索相关证据。
   - 为每个 claim 绑定 evidence span。

5. `generate_node`
   - LLM 输出结构化 node draft。
   - 禁止输出无证据强判断。

6. `validate_node`
   - schema 校验。
   - evidence quote 是否存在。
   - language consistency。
   - unsupported claims 降级或标记 review。

7. `persist_node`
   - 保存 node。
   - 更新 artifact store。
   - UI 可立即进入新层。

## 分阶段落地路线

### Phase 0：当前 MVP 固化

目标：保留现有交互，防止回归。

已基本完成：

- 多模态入口有“薄读”。
- 薄读文档模型存在。
- 本地生成 root。
- 遗漏板块和选区可生成 child node。
- 左右导航和多分支菜单存在。
- Intuecho 推荐栏有占位数据。
- 有 Vitest 覆盖基本行为。

还应补：

- `ThinReadingDocument` schema 校验。
- 本地 catalog 恢复薄读文档的测试。
- UI 截图回归。

### Phase 1：证据模型和持久化

目标：不改变 UI 大结构，先把数据打实。

工作项：

- 增加 `ThinReadingEvidenceSpan`、`ThinReadingClaim`、`generationStatus`。
- 给 `RetrievalChunk` 到 evidence span 建立映射。
- root summary 至少能引用 chunk id。
- `artifactResultClient.save` 支持 thin_reading 产物保存。
- 打开历史薄读时恢复节点树、证据、active node。

可借鉴：

- OpenDraft 的 citation database 思路。
- Open Paper 的 citation/evidence 输出分离。

### Phase 2：真实 root 生成

目标：薄读总述不再是模板。

工作项：

- 在 dev-cloud 或 agent-runtime 新增 thin-reading root endpoint。
- 输入 selected papers、metadata、chunks、targetLanguage。
- LLM 返回结构化 JSON：summary、claims、omittedSections、evidence。
- 用 Zod 校验响应。
- 校验 quote 是否能在 chunk/PDF 文本中找到。
- 失败时降级为当前模板，但标记 `generationStatus: "needs_review"`。

可借鉴：

- OpenDraft 的 phase/prompt 文件化。
- papers2dataset 的 JSON Schema response_format。

### Phase 3：真实 branch 生成

目标：遗漏板块和选区深入产生真实解释。

工作项：

- `omitted_section` branch 根据 sectionKey 检索对应原文片段。
- `selected_text` branch 先把薄读选区映射到 claims/evidence，再补充检索。
- prompt 参数参与生成。
- 生成结果保留 parent、source、evidence、closureBoundary。
- branch 任务可取消、失败可重试。

可借鉴：

- Open Paper 的工具式 evidence gathering。
- OpenDraft 的分阶段 retry 和 checkpoint。

### Phase 4：PDF 选区和原文跳转

目标：薄读不只在生成文本里选区，还能与 PDF 原文互通。

工作项：

- 薄读 claim/evidence 点击跳转 PDF 页面。
- PDF 原文选区可发起薄读 branch。
- summary 中关键短语能显示来源证据。
- evidence hover card 展示 quote、页码、置信度。

可借鉴：

- Open Paper 的 PDF highlighter 和 annotation 交互模式。

### Phase 5：Intuecho 和批注

目标：实现设计文档中的共享批注推荐。

工作项：

- 定义本地批注模型：private/public/pendingUpload。
- 定义 Intuecho recommendation API：
  - 输入 paper fingerprint、scope、user profile summary。
  - 输出 annotation id、relationship、compatibility、excerpt、author affinity。
- 推荐栏支持收起。
- 薄读节点切换时同步刷新推荐。
- 用户可将薄读段落或原文选区批注上传。

可借鉴：

- Open Paper 的 annotation/highlight/note 产品结构。

### Phase 6：外部知识扩展

目标：实现“文献闭包”后的外部扩展。

工作项：

- 计算当前 node 是否已接近论文内部证据边界。
- 若继续深入需要外部知识，明确提示用户。
- 接 OpenAlex / Semantic Scholar 查询 cited/citing/related papers。
- 外部扩展 branch 类型与论文内 branch 分开。
- 外部证据显示来源论文和可信度。

可借鉴：

- papers2dataset 的 OpenAlex BFS。
- OpenDraft 的多 API citation cascade。
- SynapseFlow 的 citation graph 可视化。

### Phase 7：评测和质量门

目标：薄读质量可量化。

工作项：

- 建立固定论文评测集。
- 指标：
  - root summary 是否覆盖核心结论。
  - omittedSections 是否合理。
  - branch 是否回答对应 source。
  - evidence quote 是否真实存在。
  - unsupported claim 占比。
  - targetLanguage 一致性。
  - 选区映射准确率。
- 在 CI 中跑小集 smoke eval。
- 大模型 eval 放手动或 nightly。

可借鉴：

- Open Paper 的 ResearchQA。
- OpenDraft 的 quality gate 和 factcheck tests。

## 推荐的技术取舍

### 不建议直接引入的东西

- 不建议复制 Open Paper 后端代码：许可证是 AGPL-3.0，且架构太重。
- 不建议把 OpenDraft 整条长文生成流水线塞进桌面端：薄读需要低延迟交互。
- 不建议把 Literature-Review-Assistant 的固定栏目直接搬成薄读 UI：这会把薄读降级为普通综述报告。
- 不建议把 papers2dataset 的 BFS 直接作为默认阅读路径：它适合外部扩展，不适合首次总述。
- 不建议直接引入 SynapseFlow 的多服务栈：当前 Liteasy 的桌面端和本地 dev-cloud 架构更轻，贸然引入 Postgres/Redis/Neo4j/MCP server 会显著增加运维面。
- 不建议以本地模板替代 live 薄读正文：fixture 只能服务测试与离线 UI 验证，不能成为任何生成失败的回退内容。

### 建议优先借鉴的东西

- OpenDraft：阶段化生成、prompt 文件化、checkpoint、quality gate、引文校验。
- Open Paper：PDF 高亮、批注、证据收集工具、citation handler、评测指标。
- Literature-Review-Assistant：固定综述问题模板，可作为薄读 planner 的候选维度。
- papers2dataset：schema-first 抽取、OpenAlex 检索、BFS 状态、失败分类。
- SynapseFlow：citation graph、MCP/SSE 接口、Zod schema、研究外延可视化。

### 对 Liteasy 的最小可行升级路径

最小闭环不需要一次做完社区和外部扩展。建议先做：

1. `ThinReadingDocument` 加 schema 和 evidence。
2. thin-reading root endpoint 真实生成结构化 JSON。
3. branch endpoint 支持 omitted section 和 selected text。
4. evidence quote 可点击回原文。
5. 保存 thin_reading artifact 到本地结果文件。
6. 建一个 5 篇论文的小评测集。

这 6 步完成后，薄读就从“可交互原型”升级为“证据支持的阅读模态第一版”。

## 风险

### 幻觉风险

薄读文本必须绑定 evidence。没有 evidence 的强判断应降级或标记 `needs_review`。

### 延迟风险

每次深入都调用大模型会慢。需要缓存 branch draft，并支持进度展示。

### UI 复杂度风险

证据、推荐、批注、外部扩展都放进一个页面会拥挤。应保持“正文居中，证据和 Intuecho 侧栏可折叠”的结构。

### 数据一致性风险

薄读节点树一旦支持增量生成，必须保证 parent/child、active node、artifact catalog、持久化文件一致。

### 许可证风险

Open Paper 是 AGPL-3.0。只能借鉴架构思想，不能直接复制代码，除非项目接受 AGPL 传染性义务。OpenDraft 是 MIT。SynapseFlow README 和仓库 LICENSE 显示 MIT。Literature-Review-Assistant 未在 README 中明确许可证，使用前需检查仓库授权状态。papers2dataset 仓库未在 README 明确展开许可证细节，使用前仍应检查其 LICENSE 或包元数据。

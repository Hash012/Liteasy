LiteasyClaw 数据模型与上云边界

依据实际代码整理，非规划稿：SQLite 迁移 db/migrations/001–005、services/dev-cloud/db/*.mjs 仓储层、requestHandler.mjs 路由、Tauri src-tauri/src/*.rs 本地存储，以及桌面端全量 localStorage 键实测。

1三个标识决定了整个数据模型

这套系统里没有单一数据库，而是「云端 SQLite + 云端 JSON 文件 + 本机文件系统 + localStorage」四个存储面。把它们缝在一起的不是外键，而是三个标识。任何跨面的数据关系都只能通过这三者成立。

users.id云端唯一真源

账号的物理主键，只存在于云端 SQLite。仅 projects / artifacts / generation_runs 等身份域表用它做真实外键。

owner_key = "user:" || users.id业务归属主键

客户端把会话 token 当 body.sessionId 发出；服务端校验后原地重写为该字符串，此后所有业务仓储都用它做归属。

  • 写入点：requestHandler.mjs:377 authorizeAccountScopedBody()
  • 本地侧同名产出：resolveLocalAccountKey()
  • 无任何 DB 外键约束——纯字符串约定

sha256(pdf bytes)跨三层的文献身份

本地库指纹、云端去重键、GROBID 解析缓存键用的是同一算法同一值空间（小写十六进制 64 位）：

  • 本地 hash_file_contents() · local_library.rs:152
  • 云端 storage_objects.content_hash · libraryStorageRepository.mjs:235
  • 解析缓存 fingerprintPdf() · grobidClient.mjs:13
  • 本地缓存文件名 <sha256>.pdf · paper_cache.rs:19
可利用的结论：同一篇 PDF 无论在本机库、云端库、还是解析缓存中，都可以用同一个 sha256 关联。这是目前唯一现成的、跨本地与云端的文献同一性通道——去重、迁移、跨设备识别都应该建在它上面，而不是新造 ID。
已知旁路：requestHandler.mjs:383 对不以 ltsy_ / user: 开头的 sessionId 直接放行（保留路演 fixture 的 demo-session-1 等命名会话）。上生产前必须关闭，否则任何人可冒用固定字符串读写他人数据。

3实体清单

按资源域分组。「归属」列写明该表用什么做归属键，这决定了它属于哪一类资源、以及能不能跨设备。

3.1 身份域 用户云端私有 已接线 001_identity_and_content.sql

表字段与约束归属

口径：会话有效期 7 天（authService.mjs:62）。库里只存 token_hash，明文 token 仅在登录/注册响应中出现一次。客户端本地只保留 {email, name, userId, sessionId(token), expiresAt, membershipTier}，密码从不落本地。

3.7 本地私有资源 不上云（设计如此）

本地文献库（文件系统）

库根路径本身不存在库里，而是存于 app_data/library-profiles/profiles/<ns>/library-root.json，ns = sha256(owner_key)[0..24]（local_library.rs:218）。

  • .liteasy-library-profile —— 账号占用标记，跨账号打开同一文件夹会被拒绝

  • .liteasy-library-index.json —— entries[] 带 sha256 与 fileSize（size 变化才重算哈希）；metadataOnly[] 收录「可列可引但无正文」的非开放获取记录，ID 由 DOI/URL/标题派生

  • app_data/artifact-catalog/…/catalog.v1.json
  • app_cache/paper-cache/<acctHash>/<sha256>.pdf —— 可丢弃；被标注即「提升」为正式入库

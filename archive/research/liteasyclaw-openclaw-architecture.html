LiteasyClaw 最终理想技术架构

这张图把 LiteasyClaw 作为“桌面优先科研 agent 工作台”的完整理想架构拆成主干、分支、边界、云端与基础设施五层。 其中紫色高亮部分代表与 OpenClaw 范式直接相关的架构单元，包括 skills、tools/action boundary、allowlist、direct dispatch 和 plugin-friendly runtime。
桌面优先 个人科研用户起步 中栏主干 + 右栏分支 OpenClaw-inspired runtime

完整理想架构

A. 用户交互层
UI Layer

左栏工作区视图

按目录层级展开母目录与子目录，是用户看见的工作区，不直接等于分析对象。

中栏模态按钮

树形展开、思维导图、PPT 等固定按钮。先指定模态，再启动主工作流。

右栏 Assistant

不是主干入口，而是导入后的分支控制台，承担问答、解释、设置、补充产物等分支能力。

选中文献集

由用户勾选并锁定形成，基本单位是单文件，是 AI runtime 的默认分析对象。

B. 主干工作流层
Mainline
工作区
→
勾选文件

形成选中文献集

导入

C. Agent 工作流层
Runtime

上下文装配

拉取已导入的选中文献集、当前模态、对话历史、画像偏好、引用上下文。

Skill Registry

把 settings.adjust、artifact.generate、paper.qa、concept.explain 等任务语义统一注册。

Action Registry

只有注册 action 才能真正改软件状态，例如 settings.update、analysis.start、artifact.open_tab。

Allowlist / Policy

按模式、身份、风险等级控制 skill 与 action 的可用性，fail-closed，不默认放开。

生成 + 审计双模型

主模型产出答案或大纲，审计模型给出可信度、问题点、返工建议。

Direct Dispatch

中栏模态按钮属于确定性直达主工作流；右栏自然语言分支则走 skill 选择与 action 执行。

D. 本地能力层
Local Engine

文献导入引擎

PDF 解析、OCR、切块、索引、本地缓存。导入状态挂在单文件上，而不是挂在整个工作区上。

本地存储

SQLite、全文索引、向量缓存、会话缓存、本地日志和权限状态。

Tauri + Rust

桌面壳负责文件系统、系统通知、权限控制、窗口生命周期和本地能力调用。

E. 云端与基础设施层
Cloud

业务服务

账号、同步、组织、推荐、订阅、后台治理。早期可薄，后期向平台扩展。

异步任务系统

长耗时导图、PPT、流程图、视频等任务放到队列与 worker 中执行。

统一模型网关

统一接入大模型、embedding、rerank、OCR、TTS、ASR，避免业务代码散接模型。

Plugin-Friendly Runtime

未来插件应优先扩 tools / skills，而不是把业务逻辑直接塞进页面组件。

OpenClaw 对应关系

紫色高亮：直接借用 OpenClaw 范式的部分
绿色主干：LiteasyClaw 自己的固定科研产品主链路，不应被纯聊天入口替代
蓝色 UI：LiteasyClaw 的产品化、桌面化、可视化交互层

OpenClaw 的 Tools → LiteasyClaw 的 Action Registry

LiteasyClaw 不应让 assistant 直接改软件，而应通过 `settings.update`、`analysis.start`、`artifact.open_tab` 这类 typed action 执行。

OpenClaw 的 Skills → LiteasyClaw 的 Skill Registry

`settings.adjust`、`artifact.generate`、`paper.qa`、`concept.explain` 等都属于任务语义层，不直接等于底层执行。

OpenClaw 的 Allow/Deny → LiteasyClaw 的模式/身份/风险控制

不是“系统里有 skill 就能调用”，而是必须按当前模式、用户身份和风险等级决定是否允许执行。

OpenClaw 的 Direct Dispatch → LiteasyClaw 的中栏模态按钮

用户已经明确指定模态，所以系统应该确定性直达主工作流，而不是再让模型猜“你是要导图还是 PPT”。

OpenClaw 的 Plugin + Skill → LiteasyClaw 后续插件生态

专注度插件、TODO、外部学术检索、组织知识源都适合用 plugin 提供能力、skill 提供工作流约束。

不照搬的部分

LiteasyClaw 不应该把用户主交互做成 slash command 式 skill 面板。它首先是科研产品，其次才是在内部借鉴 OpenClaw runtime。

最终判断

LiteasyClaw 最合理的落法不是“把 OpenClaw 做成 LiteasyClaw”，而是“把 OpenClaw 式 runtime 装进 LiteasyClaw 这个科研产品里”。 所以真正的组合是： 中栏固定模态按钮主干 + 右栏 skill/action 分支 + 底层 allowlist 与 direct dispatch 边界。

# LiteasyClaw SaaS 纠偏设计与调整方案

## 1. 文档目的与适用范围

本文档用于把 LiteasyClaw 当前仓库的真实实现状态，与 `docs/LiteasyClaw_功能与UI设计文档1.0.md` 所描述的最终预期重新对齐。

本文档的职责只有四项：

1. 明确 LiteasyClaw 的最终目标形态是什么。
2. 明确当前仓库已经实现了什么、尚未实现什么。
3. 明确当前项目与最终目标之间的偏差在哪里。
4. 明确现有文档体系与后续 SaaS 文档体系应如何分层。

本文档不是新的阶段实施计划，不替代 `docs/superpowers/plans/` 下的 phase 文档，也不重写 `docs/LiteasyClaw_功能与UI设计文档1.0.md`。

## 2. 当前项目真实状态

截至当前仓库状态，LiteasyClaw 已经实现的是一组围绕最终产品目标搭建出来的原型系统，而不是完整 SaaS 成品。

当前项目可以准确描述为三部分：

1. `products/liteasy/apps/desktop/`：客户用户端桌面原型。
   - 已具备三栏工作台、文献库、组织页、个人中心、设置页、右栏 AI 助手、多模态产物入口等可交互原型。
   - 已具备部分 `skill -> action` 安全边界和部分基于原型数据的工作流闭环。

2. `development/dev-cloud/`：开发联调用云端 demo。
   - 已提供账号演示登录、模型策略同步、推荐、文献元数据同步、组织摘要、治理摘要、模型生成和模型审计等开发接口。
   - 其职责是支撑当前桌面原型联调，不等于正式 SaaS 云平台。

3. `/admin/` 对应的内部后台 demo。
   - 已提供一个供 LiteasyClaw 平台内部查看和演示的运营/运维后台雏形。
   - 其职责是展示平台治理边界，不等于正式生产后台，也不等于客户组织管理员后台。

因此，当前 LiteasyClaw 不能被定义为“完整 SaaS 产品已经实现”，而应被定义为：

- 已完成若干阶段性交付的桌面端原型
- 已完成用于联调的开发云原型
- 已完成用于展示平台治理方向的内部后台 demo

这三个部分都对最终 SaaS 方向有价值，但它们在产品定位、工程边界和文档口径上必须与“正式 SaaS 平台”区分开。

## 4. 最终 SaaS 目标形态

LiteasyClaw 的最终目标，不应被理解为“一个桌面应用”，而应被理解为“一个以桌面端为主入口的 SaaS 产品体系”。

该体系至少应由四层构成。

### 4.1 用户端

用户端仍然可以以桌面软件作为主入口，这一点不需要推翻。

用户端负责承载：

- 工作区与文献库浏览
- 文献阅读与中栏多标签展示
- 选中文献集形成、锁定、导入与主干分析入口
- 右栏 AI 助手统一会话入口
- 组织入口、组织内管理入口、个人中心、设置、插件入口
- 多模态产物查看与回访

这里需要纠偏的不是“桌面端是否存在”，而是“桌面端是否被误认为产品本体”。

在正式 SaaS 语义下，桌面端是客户入口层，不是完整产品边界。

### 4.2 云端业务平台

云端业务平台是 LiteasyClaw 作为 SaaS 产品的核心能力层，应负责：

- 账号、认证、会话与设备管理
- 订阅、配额、套餐与付费能力
- 用户云空间与组织共享文献库
- 对象存储、文献元数据、索引与版本控制
- 联网推荐、推荐缓存、外部检索编排
- 多模态任务编排、异步任务、结果回写
- 会话、产物、审计、通知与组织级治理能力

如果没有正式云端业务平台，LiteasyClaw 仍然只能算“桌面原型 + 联调服务”，不能算完整 SaaS。

### 4.3 内部运营与运维后台

LiteasyClaw 的最终后台应面向平台内部团队，而不是面向客户普通用户。

内部后台负责：

- 模型策略配置
- 资源分配与配额控制
- 用户与组织管理
- 任务监控与失败处理
- 审计、风控、异常追踪
- 支持运营与人工干预

需要特别区分两个概念：

1. LiteasyClaw 平台内部运营/运维后台
2. 客户组织侧的组织管理能力

二者不能混为一体。

其中第二类能力不需要单独再建设一个独立后台。组织侧管理应直接内嵌在用户软件中，由具备相应权限的组织成员在软件内完成。

组织侧的基本产品规则应明确为：

- 某一级别的会员可以创建组织
- 普通用户只能加入组织
- 组织成员、共享文献库、通知、权限与组织内操作入口，都在用户端软件中完成

当前 `/admin/` 只是第一个概念的 demo seam，不应被解释为完整生产后台，也不应被误写成“组织管理员后台已经完成”。

### 4.4 Agent Workflow 与安全执行边界

LiteasyClaw 的长期核心不只是 UI，而是统一的 agent workflow。

该 workflow 应负责：

- 会话入口统一接入
- 意图识别
- 上下文装配
- `skill registry`
- `action registry`
- 文献分析、问答、推荐、画像推断、多模态生成的任务编排
- 双模型审计与可信度回写

其中最重要的工程边界是：

- 用户自然语言不能直接修改软件或平台状态
- 只有受控的 skill 才能调用受控的 action
- action 按资源 scope 和风险等级进行校验

这是 LiteasyClaw 后续继续扩展时最不应丢掉的架构主轴。

## 5. 当前实现与最终目标的偏差总表

| 模块 | 当前已实现原型 | 主要偏差 | 调整方向 |
| --- | --- | --- | --- |
| 产品定位 | 桌面工作台原型、dev-cloud、内部后台 demo | 易被误读为“桌面项目已接近完成” | 重新定义为“桌面端为入口的 SaaS 产品” |
| 用户端桌面工作台 | 三栏布局、组织页、个人中心、设置页、AI 助手、多模态入口 | 交互原型较完整，但仍偏 demo seam | 保留交互骨架，补齐正式数据与任务边界 |
| 文献库与工作区 | 工作区、选中文献集、锁定、导入、推荐、收藏已具备原型语义 | 本地资源、用户云空间、组织共享库边界未正式统一；本地文件夹与软件视图同步规则尚未正式写清 | 保留术语和交互，重建资源模型与持久化边界 |
| 中栏多模态主干 | 已有 `tree / mindmap / ppt` 原型入口与预览 | 仅为少量模态占位，尚非正式多模态体系 | 保留“中栏主干入口”原则，逐步扩展正式模态流水线 |
| 右栏助手与安全边界 | 已有统一会话、三模式、部分 `skill -> action` 边界 | 路由和执行仍以本地前端逻辑与 demo handler 为主 | 保留边界理念，迁移到正式 workflow 与云端编排层 |
| 用户画像 | 个人中心、画像开关、学术档案、清空确认原型已具备 | 画像推断、授权、外部采样和数据生命周期未正式实现 | 先做产品内画像与授权模型，再扩外部数据 |
| 组织与共享文献库 | 组织列表、组织摘要、共享库工作区切换、通知、治理摘要原型已具备 | 多租户权限、正式成员生命周期、真实共享库存储与事件流未建立 | 保留工作区切换语义，正式引入组织云资源模型 |
| 云端业务平台 | dev-cloud 提供联调接口 | 缺少正式认证、多租户、任务系统、对象存储、正式推荐与正式审计 | 从 demo 接口过渡到正式云端平台服务 |
| 内部后台 | `/admin/` 提供运营/运维 demo 展示 | 仅是展示 seam，不是正式后台 | 作为方向样机保留，后续按正式平台后台重建 |
| 插件体系 | 仅有概念和局部入口预留 | 没有正式权限模型、挂载点和生命周期 | 先定义插件宿主与权限边界，再谈生态 |
| 文档体系 | 目标文档、历史蓝图、phase 文档、QA 文档并存 | 长期目标、历史实现、原型验收口径混在一起 | 用 `docs/saas/` 建立新的正式对齐层 |

上述偏差不是在否定当前成果，而是在明确这些成果各自处于什么层级、对应什么语义、后续应怎样接续。

## 6. 分模块纠偏设计与调整方案

### 6.1 用户端桌面工作台

当前 `desktop` 方向本身没有错。

三栏工作台、最左侧窄入口栏、组织页、个人中心、设置页、右栏 AI 助手，这些都符合最终产品文档中的交互方向，应当保留。

需要纠偏的是口径：

- 当前 `desktop` 应定义为客户用户端原型
- 它承担 SaaS 的用户交互层职责
- 它不应被继续当作 SaaS 的主体边界

后续调整原则：

- 保留当前三栏工作台骨架
- 保留最左侧 `文献库 / 组织 / 个人中心 / 设置` 导航形态
- 不再以“继续堆桌面页面”替代正式云端能力建设

### 6.2 文献库、工作区与选中文献集

当前项目对以下概念的定义基本正确，应当继续沿用：

- 工作区：左栏当前可见的目录视图
- 选中文献集：在当前工作区内勾选并锁定、准备交给 AI 的文件集合
- 导入：把选中文献集送入知识引擎做解析、切块、索引等预处理

本地文献库的正式产品边界还应补充明确：

- 安装软件后，应在用户本地创建 LiteasyClaw 使用的文献库文件夹
- 本地文献库真实存在于该本地文件夹中，而不只是软件内部列表
- 收藏文献应在云端长期存储，而不是仅保存在本地
- 联网检索得到的推荐结果应缓存在云端，但属于可清理缓存，不属于长期收藏数据
- 软件中的文献库视图必须与本地文件夹内容双向同步，其语义应接近 VSCode 的资源管理器

当前偏差在于资源边界尚未正式建立：

- 本地文献库还是原型态，尚未正式落实为安装后创建并持续同步的本地文件夹
- 收藏与联网检索缓存的云端存储边界尚未正式写清
- 用户云空间尚未正式形成
- 组织共享文献库仍是 demo payload
- 三者之间的目录、元数据、权限、同步与版本关系尚未统一

后续调整原则：

- 保留现有交互语义和术语
- 不推翻“工作区 -> 选中文献集 -> 导入 -> 分析”的主干
- 明确本地文献库以本地文件夹为准，软件视图与本地文件系统保持同步
- 明确收藏属于用户云端长期数据，联网检索结果属于云端可清理缓存
- 正式重建底层资源模型，明确本地私有、用户云端私有、组织云端共享、平台治理配置、云端缓存五类资源边界

### 6.3 中栏主干模态分析

当前中栏通过模态按钮触发主分析流程的方向是正确的，也是最终产品的核心主干。

当前已实现的 `tree / mindmap / ppt` 应被定义为：

- P0 级多模态原型入口
- 用于验证主干交互、任务启动与结果回填的最小闭环

当前偏差在于：

- 模态数量距离最终目标仍有较大差距
- 多数结果仍是前端占位或轻量预览
- 还没有正式的多模态生成与回写体系

后续调整原则：

- 保留“中栏固定模态按钮是主干入口”的产品定义
- 不允许右栏命令模式取代中栏主干入口
- 将更多模态的生成能力收敛到统一异步任务和正式 artifact 生命周期中

### 6.4 右栏助手与 `skill/action` 安全边界

当前右栏最有价值的成果，不是某个具体命令，而是已经形成了如下正确方向：

- 统一会话入口
- 三种用户心智模式
- 受控的 `skill -> action` 边界

这是 LiteasyClaw 后续继续做大时最应保留的部分。

当前偏差在于：

- 意图识别仍以本地规则与字符串匹配为主
- skill 调用目标仍偏前端 handler
- action 的权限、数据 scope 和执行回写还没有形成正式平台级模型

后续调整原则：

- 保留统一会话入口
- 保留自然语言不能直接改系统状态的原则
- 将真实 skill 路由、任务编排、审计和权限逐步迁到正式 workflow 与云端编排层

### 6.5 用户画像

当前个人中心、画像开关、学术档案、清空确认、阅读数量与学术人格展示等 UI seam 是合理的。

这些成果说明：

- 产品方向上已经承认画像能力的重要性
- 前端用户心智入口已经搭出来

当前偏差在于：

- 画像推断逻辑还不是正式实现
- 授权模型还不完整
- 数据采样生命周期、撤销授权、导出、删除边界还没有正式落地
- 微信、飞书等外部数据仍停留在预留位层面

后续调整原则：

- 先做产品内画像闭环
- 先把授权、查看、清空、导出等基本数据权利做实
- 外部应用采样必须作为单独授权域，不得直接沿 demo seam 外推

### 6.6 组织与共享文献库

当前“组织共享文献库像 VSCode 打开文件夹一样切换工作区”的设计方向是正确的，应继续保留。

组织页、组织列表、通知、治理摘要、共享文献库入口这些原型工作，已经验证了产品交互方向。

同时需要补充明确：组织侧管理不另设一个独立后台，而是内嵌在用户软件中。具备相应权限的会员在软件内完成创建组织、组织配置、成员协作入口和共享资源操作；普通用户只具备加入组织与参与组织协作的能力。

当前偏差在于：

- 组织成员关系仍是 demo 数据
- 邀请、加入、退出、审批只是演示 seam
- 共享文献库并非正式云资源
- 通知、审计、配额也不是由真实事件流驱动
- “组织管理在软件内完成”这一产品边界还没有在现有文档体系中被明确写死

后续调整原则：

- 保留组织共享文献库切换工作区的交互语义
- 保留组织入口在软件内完成组织管理的产品边界，不额外派生出独立组织后台
- 明确组织创建权限属于某一级别会员，普通用户默认只可加入组织
- 正式建设多租户组织模型、成员生命周期、共享库存储、通知事件源和权限校验
- 不再把 demo 组织 payload 直接视为正式组织能力

### 6.7 云端账号、同步、推荐、任务与存储

这是当前项目与最终 SaaS 目标之间偏差最大的模块。

当前 `development/dev-cloud/` 的作用，应被明确限定为：

- 开发联调服务
- 桌面原型的控制平面与接口样机
- demo 数据回放与调试支撑

它不是正式云平台。

当前正式缺失的核心能力包括：

- 正式认证、授权与多租户会话
- 用户云空间和组织共享空间的对象存储
- 正式文献元数据模型与版本控制
- 正式异步任务系统
- 正式推荐检索、云端缓存、去重与排序服务
- 正式双模型审计与任务回写

后续调整原则：

- 所有平台化能力必须回到正式云端服务边界
- dev-cloud 只保留为开发与验收样机，不继续承担长期产品定义职责
- 后续不能以“再补一个 demo 接口”的方式替代云平台设计

### 6.8 管理后台与运维后台

这里必须明确纠偏两个概念：

1. LiteasyClaw 平台内部后台
2. 客户组织侧管理能力

当前 `/admin/` 只属于第一个概念，而且仍然只是 demo。

它的价值是：

- 帮助团队明确平台治理层将来会长什么样
- 帮助当前三端演示形成闭环

它的边界是：

- 不是正式生产后台
- 不是客户组织管理员后台，因为组织侧管理应在用户软件内完成
- 不具备正式鉴权、正式配置管理、正式监控和正式审计闭环

后续调整原则：

- 平台内部后台与客户组织管理能力分开设计
- 平台后台围绕模型策略、资源、审计、风控、任务与支持运营建设
- 客户组织侧能力则围绕成员、共享库、权限、通知与组织配置建设，并直接内嵌在用户软件中

### 6.9 插件体系

当前插件体系仍主要停留在概念层。

在最终目标文档中，插件是重要扩展方向；但在当前仓库语义中，插件还不能被写成“已形成体系”。

当前偏差在于：

- 缺少正式宿主边界
- 缺少权限模型
- 缺少挂载点设计
- 缺少生命周期与资源访问规则

后续调整原则：

- 先定义插件能运行在哪一层
- 先定义插件可访问哪些资源
- 先定义插件与 `skill/action`、工作区、组织资源之间的边界
- 在正式权限模型完成前，不把插件生态写成近期已具备能力

### 6.10 数据模型与权限边界

当前项目最需要建立的正式底座，不是再多一个 demo 页面，而是统一的数据 scope 与权限边界。

后续应明确五类正式资源域：

1. 用户本地私有资源
2. 用户云端私有资源
3. 组织云端共享资源
4. 平台治理配置资源
5. 云端缓存资源

### 6.10.1 用户本地私有资源

定义：

- 由当前用户在本机持有和控制
- 主要存在于安装软件后创建并使用的 LiteasyClaw 本地文献库文件夹
- 软件视图与本地文件夹结构保持同步

典型内容：

- LiteasyClaw 安装后在用户本地创建并使用的文献库文件夹
- 默认存放本地文献
- 工作区目录结构映射
- 本地阅读状态、部分本地临时配置和本地会话副本

生命周期：

- 跟随用户本机存在
- 用户删除本地文件、移动目录或卸载软件时发生变化

典型操作：

- 打开本地目录
- 新增本地文献
- 删除本地文献
- 调整本地目录结构

权限原则：

- 拥有者是当前设备上的登录用户
- 高风险删除、覆盖、批量移动应要求二次确认
- 自然语言不能绕过受控 action 直接改本地文件系统

### 6.10.2 用户云端私有资源

定义：

- 归属于单个用户账号
- 在云端长期持久化保存
- 不因用户切换本地工作区而自动清空

典型内容：

- 用户收藏文献的长期存储
- 与用户个人检索、学习和回访相关的持久化私有数据
- 用户个人会话历史、个人产物索引、个人偏好与画像持久化数据

生命周期：

- 按账号长期保存
- 跟随用户账号跨设备访问
- 由用户显式删除、清空或按平台规则归档

典型操作：

- 收藏文献
- 取消收藏
- 查看个人历史收藏
- 查看个人长期学习记录

权限原则：

- 拥有者是用户本人
- 仅用户本人和平台受控后台可访问
- 平台后台只能在审计、支持运营、合规或用户授权前提下处理

### 6.10.3 组织云端共享资源

定义：

- 归属于组织而不是归属于某个个人
- 由组织成员按权限共同访问
- 是组织协作与共享文献库的正式资源层

典型内容：

- 组织共享文献库
- 组织内共享目录结构
- 组织级通知、共享产物索引、组织级协作元数据

生命周期：

- 跟随组织存在
- 由组织创建、续费、解散、冻结、迁移等事件驱动变化

典型操作：

- 创建组织共享目录
- 上传、删除、调整共享文献
- 发布组织通知
- 打开组织共享文献库为当前工作区

权限原则：

- 拥有者是组织
- 访问权限由组织角色控制
- 高风险操作必须按组织角色和平台策略双重约束

### 6.10.4 平台治理配置资源

定义：

- 归属于 LiteasyClaw 平台
- 不归属于单个用户，也不归属于某个组织
- 用于平台治理、资源配置、模型策略和运维控制

典型内容：

- 模型策略
- 配额规则
- 平台风控规则
- 平台级审计配置
- 运维与支持运营配置

生命周期：

- 由平台内部团队维护
- 按平台治理流程变更

典型操作：

- 下发模型访问策略
- 调整配额
- 查看平台任务与异常
- 修改平台治理开关

权限原则：

- 拥有者是 LiteasyClaw 平台
- 只能由平台内部受权人员操作
- 不应暴露为客户组织侧可修改资源

### 6.10.5 云端缓存资源

定义：

- 存在于云端，但不属于长期主数据
- 服务于推荐、检索、问答补充、排序和短中期回访
- 必须与收藏、组织共享文献库等长期资源严格分离

典型内容：

- 联网检索结果缓存
- 推荐中间结果
- 临时检索索引
- 短周期问答补充材料缓存

生命周期：

- 按 TTL、最近访问时间、工作区变化、选中文献集变化或显式清理策略清除
- 不应作为长期收藏或正式组织资产保存

典型操作：

- 写入推荐缓存
- 读取推荐缓存
- 因工作区变化失效
- 因用户清理缓存而删除

权限原则：

- 拥有者仍可追溯到用户或组织上下文
- 但它本质上是缓存，不是长期资产
- 平台可以按缓存策略自动清理，无需保留与收藏同等级的持久性承诺

### 6.10.6 五类资源之间的关系与边界

这五类资源的核心边界应固定为：

- 本地文献库属于用户本地私有资源，不自动等同于云端长期资产
- 收藏属于用户云端私有资源，不等同于本地文件夹内容
- 组织共享文献库属于组织云端共享资源，不等同于个人收藏
- 模型策略与平台治理开关属于平台治理配置资源，不属于组织资源
- 联网检索结果属于云端缓存资源，不属于收藏或共享库主数据

由此可以直接推出若干产品规则：

- 本地删除文献，不自动等同于删除用户云端收藏
- 取消收藏，不自动删除本地原文文件
- 清理联网检索缓存，不影响用户收藏
- 打开组织共享文献库，只是把组织资源映射成当前工作区，不改变其资源归属
- 平台后台可以管理平台治理配置，但不能把组织内管理动作偷换成平台后台动作

每一类资源都应分别定义：

- 拥有者是谁
- 可以被哪些 action 操作
- 哪些操作需要二次确认
- 哪些能力只能由平台后台执行

这部分一旦没有正式定义，后续所有关于同步、共享、推荐、审计、插件和组织的能力都会继续互相污染。

## 7. 后续文档接续规则

为了避免未来继续把“历史阶段原型”“最终目标”“新一轮正式方案”混写，后续文档应遵循以下规则。

### 7.1 `docs/LiteasyClaw_功能与UI设计文档1.0.md`

该文档继续作为最终产品意图来源。

后续可以修订，但其职责始终是描述最终产品目标，而不是记录原型阶段完成情况。

### 7.2 `docs/superpowers/plans/phase0-4` 与现有 `docs/qa`、`docs/reports`

该批文档统一视为：

- 历史阶段文档
- 已实现原型阶段文档
- 历史验收与限制文档

它们保留历史语义，不在本轮 SaaS 纠偏中重命名、不回写改口径。

### 7.3 `docs/saas/`

`docs/saas/` 作为 LiteasyClaw 正式 SaaS 对齐层文档目录，后续主要承接三类文档：

1. 产品/架构纠偏文档
2. 某个正式子系统的独立方案文档
3. 面向正式 SaaS 目标的新实施计划文档

如果未来要写新的正式实施计划，应在 `docs/saas/` 下新开文档，不覆盖原有 `phase0-4` 文档。

## 8. 当前阶段结论

LiteasyClaw 当前仓库已经积累出一批对最终产品非常有价值的原型成果，包括：

- 客户用户端桌面工作台原型
- 用于联调的 dev-cloud 原型
- 用于展示平台治理方向的内部后台 demo

这些成果应被正式定义为“已经实现的历史原型阶段成果”，而不是“完整 SaaS 已实现”。

后续所有新增设计与开发，都应围绕正式 SaaS 边界继续纠偏：

- 用户端继续作为入口层深化
- 云端平台作为 SaaS 主体正式建立
- 平台后台与客户组织能力严格区分
- workflow、数据 scope 与权限边界作为统一底座重建

只有在这个前提下，当前已经做出的桌面原型、组织原型、推荐原型、后台 demo 才会真正成为正式 SaaS 产品的可继承资产，而不是继续累积语义混乱。

# 论文项目与上下文资产

实现日期：2026-09-27。需求依据：[项目上下文设计](../项目上下文设计-260927.md)。

## 使用方式

每篇工作区论文自动建立一个轻量项目。解析完成后，识别出的原文按页加入项目，识别出的图片作为独立资产加入。没有正文或图片时不创建占位内容；可以先在项目内记录笔记。

在聊天输入区点击「添加上下文」，或输入 `@` 后点击「浏览全部资产」，打开资产浏览页：

- 按类别和论文项目筛选；搜索标题、项目、说明和文件位置。
- 点击资产查看原文或图片预览，勾选后批量加入；可以同时选择多个论文、项目的资产。
- 原文、原图只读。点击「创建可编辑副本」会产生带来源关系的新笔记，后续编辑不会改写来源。
- 选中项目卡片可创建项目笔记；也可一次添加该项目当时的资产集合。
- 新生成的产物按论文来源和所选对象引用归入有关项目，同一产物只保存目录引用。
- 添加不会直接发送问题。关闭浏览页保留当前会话草稿与已添加的内容；部分添加失败会保留失败项。

候选包含项目、论文、已识别页面、原图、笔记、白板、摘录、生成产物、批注、阅读文件、已保存对话、可解释设置和内置帮助。外部笔记仍通过已有文件夹授权读取。不会为不存在的页面或未支持格式伪造正文。

## 身份、来源与持久化

`features/paper-projects/` 在现有 `ObjectStorage` 保存 `paper-project/project/` 与 `paper-project/asset/` 记录。项目身份由 scope 和 paperId 确定，项目标题变化不改变身份。目录只保存引用和展示信息，不是另一份产物正文数据库。

原文和原图使用 `source.document`；图片字节复用内容哈希附件。来源更新由受信任的解析同步执行，产生新 revision，旧引用保持原版本。项目资产保留论文、页码与已有文档 hash。副本使用 `content.note`，保留 `sourceRefs`、`derivedFrom` 与附件描述。

加入上下文时固定所选成员和 revision。项目内派生笔记在选择时解析最新版本；来源和明确的引用保持固定版本。对象可被多个项目引用，不以路径、标题或所在项目重新复制身份。

同步采用按 scope 的串行队列和来源缓存；重复渲染不重新写入正文，reader 成功保存 fulltext 会合并触发对应论文更新。坏图片、单篇读取失败不会阻断其他项目。账号切换隐藏旧目录并拒绝迟到的读取、预览与上下文结果。

## 本轮实际读取范围

聊天对象上下文启用 `balanced` 策略：默认约 6,000 个文字 token 的估算预算，按资产均衡分配并结合问题选择相关片段，最多 500 个引用。每项记录完整、部分或未覆盖状态，以及固定源文本的字符范围。回复旁的「本轮读取范围」显示覆盖明细；部分选段不能当作全文审阅。既有需要整项读取的调用仍可使用默认 `strict` 策略。

白板加入时同时保存成员、位置、尺寸和连线的结构快照，发送时不读取后来变动的结构。图片以受限字节输入模型，快照和运行记录仅保存附件描述，不重复持久化 base64。发送前再次验证对象、scope、图片长度与 hash。

图片限制为每轮最多 12 张、合计 5 MiB，模型 JSON 请求上限 8 MiB。直连 OpenAI 兼容 Chat Completions、Anthropic，以及正式 API / dev-cloud 的 OpenAI Responses 路由传递真实图片；模型本身必须支持视觉。不支持图片的 provider 明确拒绝，不能无提示退成纯文本。Responses 的 `input_image` 和 base64 data URL 格式依据 [OpenAI Docs](https://developers.openai.com/api/docs/guides/images-vision)。

## 边界

这是应用内逻辑项目和统一上下文目录，不是 OS 挂载文件系统，也不表示全 provider VFS、跨设备项目同步或通用 AI 变更集已经完成。项目元数据仍使用现有本机对象存储；正式模型 API 的图片代码需要部署后才对线上服务生效。未识别的图片不会因建立项目自动获得 OCR/视觉描述。

长文选段可通过更具体的问题或重新选择页面继续读取；当前没有模型自主反复补读整库的工具循环。上下文和图片均有明确上限。

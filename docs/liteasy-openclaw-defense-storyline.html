T_IM 为什么是整场亮点

它把普通 AI 问答升级成了真正可视、可回溯、可分层的精读体验。

1

2
AI 可以连续划线、逐段解释，形成像老师精讲论文一样的链条。
3

4
用户不再只是听答案，而是在原文中被带着完成理解过程。

关键概念，不要只停留在名词

这一段是给主讲人和答辩成员“心里有数”用的。每个概念都要讲到：它具体负责什么、边界是什么、在 Liteasy 里会长成什么样。

工作区 vs 选中文献集

是什么：工作区是用户当前打开的文献树；选中文献集是当前真正送进 AI runtime 的分析对象，通常由 `selectedPaperIds` 表示。
不是什么：不是“打开了整个文件夹，AI 就默认理解整个文件夹全部内容”。
在 Liteasy 里：左栏负责管理工作区，勾选并锁定后形成稳定分析边界，后续问答、导图、PPT 都优先基于这组已锁定文献。

Context Assembly

是什么：在调用模型前，把 `selectedPaperIds`、当前页面锚点、对话历史、用户画像偏好、检索到的 chunk 一次性拼成上下文输入。
不是什么：不是把整篇 PDF 原样丢进模型，更不是只拿用户最后一句话去问。
在 Liteasy 里：它决定 AI 到底是在回答哪几篇论文、哪一页、哪一段，以及要不要沿用之前的解释链。

Skill Registry

是什么：任务语义注册表。它告诉系统“这是名词解释”“这是论文问答”“这是产物生成”“这是设置修改”。
不是什么：不是直接操作系统或直接改软件状态的底层接口。
在 Liteasy 里：典型 skill 可以是 `concept.explain`、`paper.qa`、`artifact.generate`、`settings.adjust`。它决定流程模板，不负责真正落地执行。

Action Registry

是什么：系统允许执行的结构化动作列表，每个 action 都有明确输入、输出和副作用。
不是什么：不是模型想到什么就能随便调用什么。
在 Liteasy 里：可以长成 `settings.update`、`analysis.start`、`artifact.open_tab`、`workspace.lock_selection`。只有注册过的 action 才能真正改 UI 状态、开标签页或改设置。

Allowlist / Policy

是什么：权限与风险策略层。它决定某个模式下、某个用户身份下、某类操作是否允许执行。
不是什么：不是“有 skill 就一定能跑”，也不是所有命令都默认放行。
在 Liteasy 里：像“清空画像”“删除文献”“关闭同步”这类高风险动作，都应该先过 policy，再要求二次确认，默认 fail-closed。

Direct Dispatch

是什么：当用户意图已经足够明确时，不再让模型猜，而是直接进入确定性的执行链。
不是什么：不是所有交互都必须先聊天、再让模型二次判断用户想干什么。
在 Liteasy 里：中栏“思维导图 / PPT / 树形展开”按钮就是 direct dispatch；右栏自然语言命令则仍需先解析，再路由到对应 skill 和 action。

Session Isolation

是什么：把一次问答或一次分析绑定在明确的上下文边界里，避免不同论文、不同工作区之间串台。
不是什么：不是所有会话共用一个大缓存，更不是今天讲过的论文自动污染明天的新工作区。
在 Liteasy 里：边界至少包括 `workspace_id`、已锁定文献集、当前会话历史与当前模式。

Local Knowledge Engine

是什么：把 PDF 从“文件”变成“可检索、可引用、可跳转知识对象”的本地引擎。
不是什么：不是简单把文件路径记下来，也不是只在前端展示一个 PDF 阅读器。
在 Liteasy 里：它会负责 PDF 解析、OCR 回退、文献切块、全文索引、锚点映射和本地缓存，让问答与划线能精确回到原文位置。

统一模型网关

是什么：统一接入 LLM、embedding、rerank、OCR、TTS、ASR 等模型能力的单一入口。
不是什么：不是每个业务模块自己随手连一个模型 API。
在 Liteasy 里：这样才能统一记录 provider、model、token、耗时、失败重试与成本，也方便未来切换模型供应商。

双模型生成与审计

是什么：一个模型负责生成，另一个模型负责检查“有没有答到点上、有没有乱引、有没有幻觉、引用是否足够”。
不是什么：不是为了显得高级而无差别叠两层模型，也不是所有短命令都强制走双模型。
在 Liteasy 里：深度文献分析、PPT/导图大纲、重要解释链优先走双模型；简单设置类命令可以只走单模型或不走模型。
讲的时候可以用这句区分： skill 解决“这次任务属于哪一类”，action 解决“系统最后具体执行什么”，policy 解决“这件事能不能做”，direct dispatch 解决“用户已经说得很明确时，不要再让模型多猜一层”。

两条最关键的工程执行链路

如果评委追问“你们到底怎么做到”，这两条链路最值得讲，因为它们能把抽象概念落到真实控制流与数据流上。

链路 1：命令控制不是聊天，而是结构化执行

以“关闭联网推荐”为例，系统理想执行链是：自然语言先被识别为设置变更意图，再被结构化成命令对象，之后由 policy 校验，再落到一个明确 action 上执行。

{
  "intent": "update_setting",
  "target": "network.recommendation.enabled",
  "value": false,
  "skill": "settings.adjust",
  "action": "settings.update"
}
工程含义：这样做的好处是，模型只负责理解用户意图，不直接接触高风险副作用；真正改设置的是可审计、可回滚、可测试的 action 层。

链路 2：论文问答不是只出答案，而是带依据地回链原文

以“解释这篇论文的 method”为例，系统理想执行链是：先装配上下文，再检索 chunk，主模型生成回答，审计模型给出评分与问题点，最后把答案回写到聊天与 PDF 锚点。

{
  "workspace_id": "ws_001",
  "selected_paper_ids": ["paper_a"],
  "anchor_refs": ["paper_a:p12:para_03"],
  "skill": "paper.qa",
  "retrieval": ["chunk_42", "chunk_57"],
  "audit": {
    "score": 0.84,
    "issues": ["结论缺少实验段落引用"],
    "suggested_revision": "补充第 14 页实验设置定位"
  }
}
工程含义：最后产物不只是右栏的一段话，还应包括引用定位、PDF 划线、Concept Map 节点或新标签页产物。

当前原型与下一阶段，要明确分界

这部分是防止“讲大了”的关键。越讲工程化，越要把已经有的和下一步必须补的分开。

当前原型已经能支撑哪些说法

桌面形态：三栏工作台骨架已经存在，产品形态不是空想。
状态切片：当前仓库已有工作区勾选锁定、助手模式切换、导入任务状态等最小状态切片。
技术底座：`Tauri 2 + React + TypeScript + Rust + Vitest` 这条桌面技术栈已经落下来。
可以讲的结论：“我们已经完成桌面原型与核心交互骨架，正在继续把文献引擎与 runtime 做实。”

下一阶段必须补齐的工程件

本地文献引擎：PDF 解析、OCR、切块、索引、锚点映射，否则“划线回链”还只是设计。
命令路由：从自然语言到 `skill + action` 的命令结构化层，否则“AI 控制软件”还不够可控。
可信回答：检索、引用绑定、双模型审计，否则“更可信”还缺少工程抓手。
异步任务：PPT、视频、复杂导图需要任务队列和 worker，否则前端会被长任务拖死。

答辩高频问题

1. 为什么参考 OpenClaw？

因为它在复杂 AI 能力组织方式上很成熟，尤其是 skill、routing、plugin、policy 这些 runtime 思想。我们借鉴的是“怎么让 AI 走可控流程”，而不是把 Liteasy 做成另一个多渠道聊天壳。

2. 你们和普通论文问答工具有什么不同？

我们的重点不是“回答一句话”，而是把问答、原文定位、连续划线、Concept Map、多模态产物和后续学习动作接成一条线。

3. 为什么是桌面端，不是网页？

因为论文学习强依赖本地文件、工作区、并排阅读、多标签页和系统级权限控制，桌面端更适合承载重交互阅读场景。

4. 你们的 AI 为什么更可信？

第一，回答尽量绑定原文定位与 chunk 引用；第二，关键分析结果走双模型生成与审计；第三，软件操作不靠模型随意执行，而是走结构化 command、typed action 和 policy 校验。

5. 插件在这里的作用是什么？

插件不是给页面塞更多按钮，而是把专注度管理、TODO、外部知识源等能力以可管理、可授权的方式接入同一个 runtime，让扩展能力仍然遵守统一的 action 与 policy 边界。

如果说 OpenClaw 证明了 AI 应用应该怎样组织能力，那么 Liteasy 做的，就是把这套能力组织方式， 真正变成一个适合论文精读、适合教学式讲解、也适合长期科研成长的桌面产品。

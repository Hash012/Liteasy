# Liteasy 用户手册设计说明

**内容基线：0.1.28 / c37bb2f0fde9fca8dd8dbbc409cb8cfeea030c7a。核对日期：2026-10-02。**

这不是把开发文档改成更长的 README，而是建立一套“用户遇到任务时找得到、照着做时能确认结果、功能变化后能追溯更新”的产品帮助系统。本包交付 48 篇正文、12 个主题、独立离线浏览版、兼容现有接口的嵌入包，以及接入和验证工具。素材是本次新写内容，不使用第三方产品标识、字体文件或截图冒充 Liteasy 界面。

## 1. 从当前代码出发，而不是另起一套网站

当前 `builtinHelpProvider.ts` 只注册入门与评论 Review 两篇正文，却列出五个主题。白板、Agent、设置等目录没有对应教程。模块 README 对正文数的描述也落后于注册文件。[S01–S03]

已有架构值得保留：`HelpContentProvider` 负责目录、搜索和 Markdown 读取；`HelpPanel` 只消费 `HelpViewModel`；`useHelpController` 处理查询、错误重试和过期结果；`HelpPort.open` 提供上下文入口。Provider 以 `providerId + articleId` 寻址，文章正文通过 `MarkdownContent html="skip"` 渲染。[S01–S05]

因此本包选择**先补内容和内容治理，不重写业务界面**。保留导出名 `builtinHelpProviders` 和 `liteasy` 命名空间，保留两条原有文章 ID，并兑现原 README 里的 `reading.selection` 示例。这样既服务 AppShell，也覆盖直接读取内置手册的助手上下文目录。[S01、S03、S25]

独立 HTML 浏览版展示更丰富的任务首页、文章目录和关联阅读，但它不自动替换应用 HelpPanel。把独立预览与已接入功能分开，是避免“设计演示已经实现”误解的重要交付边界。

## 2. 对标哪些产品，借什么，不借什么

这些是从官方页面提炼的设计依据，不是对竞品转化率、留存或易用性分数的实证比较。所有“建议、目标、阶段”均为本次方案，不冒充 Liteasy 已测得的产品指标。

## 3. 核心原则

### 任务优先，概念按需

新用户要完成的是“读这篇论文并记下疑问”，不是先理解 AgentAssetAdapter。首篇从一个无敏感信息的小 PDF 开始，先完成不需要模型的导入、阅读和保存，再增添模型连接。先让用户得到可验证结果，再解释上下文、画像和快照。

按模块目录机械抄写容易产生“每个功能都介绍了，但用户仍不知道下一步”的手册。这里以任务串起功能，同时保留专题文章供返回查阅，避免一条教程无限膨胀。

### 三种用户都能迅速进入

首次用户走入门闭环；已有用户用搜索找到具体操作；遇到故障的用户从现象进入诊断。高级用户不必重读入门，直接查 MCP、同步冲突、平台限制和设置表。

### 每篇都有结果检查

导入不是出现条目就结束，要能打开正文；保存不是切换后草稿还在，要重开后仍存在；下载不是找到 URL，要有真实 PDF；模型返回不是研究结论正确，要回到证据。结果检查同时是用户自测脚本和维护者回归场景。

### 默认状态和风险前置

增强推荐默认关闭、画像记录另开、WebDAV 的对话与画像类别默认开启、外部目录和 API key 默认关闭。这类细节会改变隐私决定，必须在用户做选择之前出现，而不藏在技术附录。[S10、S15–S16]

“关闭同步不删除远端”“停止共享不撤回已收到内容”“取消不回滚已提交效果”直接写进对应操作，不让用户推断撤销能力。[S16–S18、S21]

### 事实与状态比营销完整性更重要

优先核对实际入口代码，其次看近期实现记录；计划、规格和 archive 不作为已上线能力。无法确认的具体导出格式、完整工作流界面和生产部署，以明确限制说明，不编造按钮。对源代码已有但缺实机验收的功能，提供条件式教程与验收清单。

### 单一正文来源，多个呈现出口

Markdown 正文和 manifest 是权威源。应用 TS 注册表、HTML 预览、完整 Markdown 和目录表都由它生成。维护者只改源稿，避免修了一份 PDF 却忘了应用内帮助。本次不新增内容服务器、账号或追踪脚本。

## 4. 信息架构与阅读层级

12 个主题覆盖开始使用、阅读、白板、AI、发现、设置、存储、同步、外部 AI、安全、排错与参考。正文共 48 篇，原有两个 ID 留存，新增分类只扩展内容提供方，不改变上层接口。

一篇正文通常包含：一句用途、适用条件、准备、明确步骤、应该看到什么、失败路径。解释型文章可改用对照表，参考型文章以索引为主；不强迫所有内容使用同样数量的段落。正文从二级标题开始，避免与 HelpPanel 自带一级标题重复。

首页优先展示四条用户路线，不把 48 个链接堆成唯一入口。文章内的“相关内容”来源于 manifest 关系；独立 HTML 可点击，当前嵌入面板仍以已有目录／搜索定位，不声称存在未经实现的 help:// 路由。

## 5. 搜索设计

保留多词 AND 语义，符合已有 `chatgpt 隧道` 回归。增加 NFKC 规范化和中文／英文常用别名，按标题、别名、摘要、正文加权排序；空查询按编辑顺序稳定输出。单个中文短语采用直接匹配，不谎称已经具备语义搜索、自动纠错或无限语言覆盖。

本地索引不向服务器发送查询，不用 LLM 回答替代正文。先测试用户会说的“连不上、文件不见、模型、换盘、坚果云、MCP”，再决定是否需要更复杂检索。无结果时明确提示清除筛选或改词，而非生成似是而非的答案。

## 6. 视觉与交互

独立浏览版采用紧凑顶栏、清晰的搜索输入、主题侧栏和宽度受控的正文。正文以系统字体、舒适行高和有限强调色为基础；较长表格有独立横向滚动，不拉宽整页。浅深主题只影响浏览版，不修改 Liteasy 设置。状态和风险不仅用颜色表达。

交互反馈必须对应真实动作。没有后端的“反馈”只复制本机问题模板，不显示“提交成功”。示意图标为概念图，不借外观暗示产品当前已有某个按钮。截图素材规范另外交付，待最终安装包核对后拍摄，不能用浏览器 mock 或竞品截图替代真实应用。

## 7. 发布与维护

先在源码分支接入内容，跑内容契约测试和已有帮助回归，再执行前端构建。随后在最终 Windows 安装包中实测 F1、搜索、正文与高风险入口。功能的真实模型、服务器和手机联调不由静态手册测试代替。

建议发布门槛：没有不存在的文章引用；高风险默认值全部有依据；用户能完成首次阅读闭环；无网络也能读帮助；原有稳定 ID 继续工作；未知语言显式回退；未完成的平台验收清楚标注。这些是拟议的门槛，不是本次已经通过全部产品验收的声明。

后续再考虑 HelpPanel 的首页卡片、文章内导航、平台筛选和版本选择。接口扩展与 UI 功能应另开 PR，避免把内容扩充捆绑成大规模界面重构。

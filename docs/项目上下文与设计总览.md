# LiteasyClaw 项目上下文与设计总览

> 用途：这是供后续 AI 会话、开发者和产品讨论快速建立共同语境的“项目事实源”。讨论方案前，先区分“已实现”“演示/MVP”“目标设计”，不要把后两者当作生产能力。

## 1. 项目在做什么

LiteasyClaw 是桌面优先的科研阅读与学习 Agent 工作台。它的目标不是替代通用聊天工具，而是把科研用户的完整工作流收敛为可持续的闭环：

```text
建立/打开工作区 → 勾选并锁定文献 → 导入（解析、切块、索引）
→ 问答或指定分析模态 → 生成可追溯的学习产物 → 沉淀为知识、会话与画像
```

产品差异化在于：Agent 使用当前工作区、选中文献集、导入状态、组织与用户画像等显式上下文；涉及论文的回答和产物应能回到原文来源；自然语言只能提出目标，不能绕过策略直接修改应用状态。

首发用户是个人科研用户，长期预留组织协作、平台治理、插件/MCP 和云端能力。产品采用“全景架构、分阶段交付”的策略：大模型和多模态能力优先调用第三方 API，本地/自建侧优先承担检索、缓存、任务编排、权限和同步。

## 2. 用户工作台与核心概念

桌面端采用三栏工作台：左栏负责文献库、推荐、收藏、组织与个人中心；中栏负责 PDF 阅读和多模态产物标签页；右栏是 AI 助手、运行时上下文和执行反馈。

| 概念 | 定义与边界 |
| --- | --- |
| 工作区 | 当前可见的文献目录视图；可为本地文献库或组织共享资料区，切换不是合并。 |
| 选中文献集 | 用户在当前工作区勾选并锁定、准备交给 AI 的文件集合；分析功能应依赖其快照，而非复选框 UI。 |
| 导入 | 对选中文献执行解析、切块、索引等预处理；当前流程仍以桌面端 mock 为主。 |
| 分析/产物 | 在已导入的选中文献集上进行问答、摘要、比较、脑图、表格、PPT 等输出。 |
| Agent | 理解目标、装配上下文、规划受控动作、请求确认并呈现结果的工作台代理。 |

右栏保留解释、问答、命令三种用户心智，但技术上应收敛为同一会话入口下的检索解释、控制执行和深度分析路由。P0 产物优先级为问答式解析、树形展开、思维导图、PPT；流程图、数据可视化、苏格拉底/费曼学习为后续层级；播客、视频与动图不属于当前承诺范围。

## 3. 架构原则与当前结构

当前仓库按业务域组织：`products/liteasy/` 包含桌面端、管理端和正式 Liteasy API；`products/intuecho/` 包含论坛 Web、独立 API 与契约；`products/marketing/` 是独立营销站。跨产品身份生命周期适配器位于 `platform/identity-service/`，本地真实开发 API 和维护工具位于 `development/`，基础设施编排位于 `deployment/`。工程文档在 `docs/`，历史材料在 `archive/`。

必须保持依赖方向：

```text
shell/layout → controllers → feature modules → shared types / clients
```

`AppShell` 只负责组合。跨模块编排进入 `src/app/controllers/`；feature 不得反向导入 `layout` 或 `AppShell`。状态变更应统一表达为注册 action，使按钮、自然语言和未来快捷键使用同一执行边界。新独立界面先归类为 DockItem；移动或关闭 tab 不能删除领域数据。

关键功能模块包括：`workspace`、`selection`、`import`/`retrieval`、`assistant`、`agent-runtime`、`agent-core`、`actions`/`skills`、`artifacts`、`generative-ui`、`dock`、`account`/`network`、`models`、`collection`/`recommendations`/`metadata`、`organization`、`library`、`profile` 与 `settings`。

## 4. Agent 与生成式 UI 的设计边界

运行路径应保持为：

```text
用户输入 → AgentCore.prepareTurn（配置、记忆、能力、预算、上下文）
→ agent-runtime（语义规划、契约校验、策略裁决、注册 action 执行）
→ AgentCore.observeTurn（观察、失败、预算）→ Assistant UI / 产物标签页
```

`agent-runtime` 是单次交互的执行边界：模型可返回结构化计划，但只能调用已注册 action；plan validator、policy 和确认机制必须在执行前生效。低风险布局、主题、面板类操作可即时或乐观执行；删除、覆盖、上传、组织资料写入、付费资源和画像采样必须确认。缺少选中、未锁定或未导入文献时，应澄清而不是假装掌握论文上下文。

生成式 UI 不是让模型输出 React/CSS 或直接操作 DOM。模型或规则只能在受 schema 约束的 UI DSL 中选择组件、文案和数据投影；`DynamicCanvas`、组件/数据源注册表、DSL/UX validator 与 execution journal 负责渲染、质量门和可回放审计。

## 5. 已实现的能力与真实边界

| 状态 | 当前内容 |
| --- | --- |
| 已有可运行骨架 | 三栏工作台、Dock 布局、工作区/选择/锁定、导入状态、PDF 与产物 tab、右栏助手、运行时上下文面板、命令解释与受控 action。 |
| Agent 运行时 | 语义 action 规划（模型辅助并有确定性回退）、计划校验、策略与确认、任务/产物事件、常见布局/设置/组织资料区操作。 |
| Agent Core | 默认 `agent.md`、skill/plugin/MCP 目录、turn 级上下文装配、memory 检索、预算/重复失败保护；命令与问答/解释路径已接入。 |
| 开发云 | 真实注册、Argon2id 凭据、持久会话、audience 隔离、事务化文献树/对象引用、推荐与收藏、RBAC/MFA/审计；只调用显式配置的真实 provider，不提供 mock 业务结果。 |
| 组织与画像 | 组织成员/角色/策略、共享文献库、团队批注、通知/治理、个性化采集关闭与服务端清除链路。 |

必须正视的边界：当前 `dev-cloud` 使用 SQLite 和本地私有对象目录，且在 staging/production 环境强制拒绝运行；正式事务数据库、S3 API 对象存储、IdP/MFA 设备、备份恢复和 Windows Tauri E2E 仍是发布门禁。模型审计中的确定性规则不等于外部模型评测；插件市场、正式 MCP 注册和跨设备同步也不在当前完成范围内。

## 6. 性能、准确性与体验要求

当前规格强调的是可感知性能与正确性，尚未冻结端到端毫秒级 SLA；提出数字指标时应先建立基线和测试数据集。已确认的要求如下：

- 路由和上下文校验应快速返回，不能被慢模型调用阻塞。
- 长任务必须任务化，先显示进度、pending artifact tab 或任务卡，再等待最终内容。
- 重复上下文装配应优先读取本地快照，避免重复网络请求。
- 低风险常用命令应在不超过两步的交互内完成；失败要给恢复路径。
- 涉及论文的问答必须带原文片段或定位；产物元数据必须保留来源；所有状态变更必须有结构化事件/审计记录。
- UI 需适配窄右栏；不要以嵌套卡片、装饰性大块或无状态反馈换取“AI 感”。

建议后续为关键路径分别量化：本地命令响应、上下文装配、检索首结果、任务首状态、产物首屏、模型完成、内存检索命中率/污染率和失败恢复率。

## 7. Agent Memory：当前现状与下一步

当前实现在 `products/liteasy/apps/desktop/src/app/features/agent-core/`：`memoryStore.ts` 是前端会话内内存 store；每轮按用户消息检索至多 4 条 memory；排序为“关键词命中 × 4 + 重要性（高/中/低）”。memory 类型为偏好、画像、项目、经历，字段包含 `id`、`namespace`、`summary`、`importance`。命中的摘要由 `contextAssembler` 注入模型/规划上下文。

当前限制：刷新即丢失；没有 SQLite/Tauri 持久化、过期策略、显式删除/禁用 UI、写入提取流水线、注入检测、语义检索、跨设备同步或完整 trace/audit。默认配置虽声明“写入需扫描、命名空间隔离”，但这些治理能力尚未形成完整执行链路。

建议 memory 后续按以下顺序推进，而非直接堆向量库：

1. 定义稳定数据模型：增加 `createdAt`、`updatedAt`、`lastAccessedAt`、`source`、`confidence`、`status`、用户/工作区/组织 namespace 和可删除标记。
2. 落地本地持久化：优先 Tauri/Rust SQLite，提供迁移、加密策略、导出/清空和离线可用；组织记忆不得与个人记忆混检。
3. 建立写入治理：仅从可信事件或用户确认中提取候选 memory；过滤密钥、提示注入、越权指令和原始私密文档内容；先预览、可拒绝、可撤销。
4. 改进检索：先 namespace/权限过滤，再用关键词、重要性、新鲜度、任务/工作区相关性混排；有基准与规模需求后再加入 embedding/FTS。
5. 可观测与评测：记录“为何命中、注入了什么、是否被采用”；建立误召回、遗漏、过期、污染和跨 namespace 泄漏的测试集。

Memory 的产品原则是“保存长期可复用事实，而非完整聊天记录”。严禁存储 API key、token、高风险指令或未经允许的原始隐私文件内容。

## 8. 后续会话的协作方式

讨论或实现新能力时，请先说明：目标用户路径、涉及的 feature owner、是否改变 action/skill 契约、需要哪些运行时上下文、风险等级与确认策略、数据边界（本地/云端/组织）、失败与恢复路径、测试位置和验收指标。

```text

请输出：模块边界、数据模型、运行时事件/契约、风险与确认、迁移步骤、测试矩阵、性能指标与未决问题。
```

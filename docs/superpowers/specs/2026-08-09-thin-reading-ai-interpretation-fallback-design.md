# 薄读四档证据支持与 AI 理解兜底设计

## 1. 摘要

本文定义 Liteasy 薄读正文的四档证据支持模式，并将“没有论文内外依据，仅由
AI 给出独立理解”从生成失败改为严格受控的第四档。

四档为：

1. 仅原文献闭包内证据支持；
2. 原文献证据与可信外部来源共同支持；
3. 仅可信外部来源支持；
4. 论文内外均无支持，仅 AI 独立理解。

第四档不是普通证据不足的通用回退。只有用户请求必须越出论文闭包，并且没有可复用
的既有可信来源，同时外部检索全部失败、未得到可信结果，或候选来源在复核后全部失效
时，系统才允许生成第四档正文。界面必须使用独立背景和固定声明清楚表达该边界。

本文是实施设计，不表示该行为已经实现或通过生产验收。

## 2. 目标

1. 用独立、可持久化的数据状态准确表达四种正文支持来源。
2. 在必须越出论文闭包但可信外部来源不可得时，允许用户继续获得明确标记的 AI 理解。
3. 保持论文内请求和其他质量失败的现有硬门，不让第四档成为隐式绕过证据约束的路径。
4. 让第四档的触发原因、检索结果和生成模式可审计。
5. 在界面上同时使用文字、图标和背景表达第四档，不仅依赖颜色。
6. 保持旧薄读文档可读，且不把旧数据中的空证据误判为 AI 理解。

## 3. 非目标

- 不允许用户为任意论文内问题手动关闭证据门。
- 不把模型预训练知识、常识或推理伪装成论文结论或外部研究结果。
- 不在第四档生成引用、参考文献、论文证据标记或可信来源角标。
- 不因模型调用失败、JSON 解析失败、普通质量门失败或用户取消而进入第四档。
- 不把第四档正文作为后续节点的论文证据或可信外部来源。
- 不修改外部来源的可信度、可追溯性和关系真实性标准。
- 不把 readiness、测试通过或本地开发行为描述为生产环境已经验收。

## 4. 现状与问题

当前 `ThinReadingClosureState` 只有 `inside_paper`、`near_boundary` 和
`outside_paper`。它表达阅读深度相对论文闭包的位置，不能表达正文实际使用了论文证据、
外部来源，还是二者共同支持。

当前外部检索路径会在以下位置停止生成正文或返回闭包边界提示：

- 所有检索请求都失败，且没有既有来源可复用；
- 检索完成，但筛选和排序后没有可信、可追溯来源；
- 候选来源未通过正文命题复核，定向换源仍为空，此时只返回闭包边界提示而不是用户所需正文。

此外，薄读质量门要求每个正文句至少映射一个论文 evidence ID 或可信 external source
ID。只删除外部检索处的异常仍会在模型解析和句级可追溯性检查中失败。因此第四档必须贯穿
编排、生成契约、质量门、持久化、投影和 UI，不能通过空数组或 CSS 猜测实现。

## 5. 核心状态模型

### 5.1 节点支持模式

新增独立联合类型：

```ts
export type ThinReadingSupportMode =
  | "paper"
  | "paper_and_external"
  | "external_only"
  | "ai_interpretation";
```

`supportMode` 持久化在 `ThinReadingNodeSeed` 和 `ThinReadingNode`。新生成节点必须显式写入；
读取旧文档时允许字段缺失，并由兼容投影推导显示模式。

`closureState` 和 `withinPaperClosure` 保留原职责：

- `closureState` 表达读者处于论文闭包内、临近边界或闭包外；
- `withinPaperClosure` 表达当前节点是否仍处于论文闭包内；
- `supportMode` 表达正文实际由哪类依据支持。

三者不能互相替代。`paper_and_external`、`external_only` 和 `ai_interpretation` 的
`withinPaperClosure` 均为 `false`；`near_boundary` 仍可以与 `paper` 同时出现。

### 5.2 句级支持模式

`ThinReadingSummarySentence` 增加显式 `supportMode`。正常模式下由经过白名单校验的句级
ID 确定，而不是由模型自由声明：

| 论文 evidence ID | external source ID | 句级模式 |
| --- | --- | --- |
| 有 | 无 | `paper` |
| 有 | 有 | `paper_and_external` |
| 无 | 有 | `external_only` |
| 无 | 无 | 仅受控第四档可为 `ai_interpretation` |

第四档所有正文句必须为 `ai_interpretation`，论文和外部 ID 均为空，并保留
`status: "unsupported"` 表达其没有来源支持。质量门只在节点已由编排器授权为第四档时允许
这种组合。

节点模式由全部正文句和节点证据集合聚合验证。节点声明与实际 ID 不一致时生成失败，不做
静默纠正。

### 5.3 旧文档兼容

旧节点没有 `supportMode` 时按已持久化的有效引用推导：

1. 同时有论文和外部引用，推导为 `paper_and_external`；
2. 仅有外部引用，推导为 `external_only`；
3. 其他情况投影为 `paper`。

旧节点的论文和外部引用都为空时不得推导为 `ai_interpretation`。第四档必须有新版本显式
状态和生成审计，历史空数据继续按旧兼容路径显示，不能获得第四档质量门豁免。

## 6. 外部检索结果契约

外部检索不再只返回来源数组或抛出普通错误。编排层使用区分联合：

```ts
type ThinReadingExternalAcquisitionResult =
  | {
      kind: "sources";
      sources: readonly ThinReadingExternalSource[];
    }
  | {
      kind: "unavailable";
      reason:
        | "all_routes_failed"
        | "no_trusted_sources"
        | "verification_exhausted";
      audit: ThinReadingExternalFallbackAudit;
    };
```

`sources` 分支必须至少包含一个通过现有可信度和可追溯性筛选的来源。空数组不属于该分支。

`unavailable` 只表示来源获取边界，不吸收取消、模型、格式或程序错误：

- `all_routes_failed`：计划中的支持、质疑和上下文检索均拒绝或在调度前不可用，且无既有来源；
- `no_trusted_sources`：至少一路完成，但合并、去重、可信度和可追溯性筛选后为空；
- `verification_exhausted`：来源进入生成后未直接支持正文命题，定向换源仍未得到替代来源。

`AbortError` 始终继续抛出。检索编排之外的异常也继续走现有失败路径。

审计记录路由意图、每路完成状态、既有来源数量、候选数量、可信来源数量和标准化原因类别。
不持久化异常堆栈、凭据或其他敏感配置。

## 7. 第四档触发规则

第四档必须同时满足以下不变量：

```text
requiresThinReadingExternalKnowledge(context) === true
AND remainingTrustedSources.length === 0
AND externalAcquisition.kind === "unavailable"
AND signal is not aborted
```

其中第一项必须由现有解释计划和用户请求共同判定，模型输出不能将普通论文内请求自行升级
为必须越界。`remainingTrustedSources` 是初次筛选或命题复核移除失败来源之后仍可直接支持
生成的集合，不是未经复核的原始候选集合。

如果初次获取到了候选来源，但全部在命题复核中失效，则只有在定向换源也返回
`verification_exhausted` 后才能转入第四档。系统必须重新生成完整正文，不能保留未获支持的
来源句再移除引用标记。

以下情况不进入第四档：

- 请求仍可在论文闭包内回答但证据不足；
- 有至少一个既有可信来源可复用；
- 有至少一个检索分支返回可用可信来源时先执行正常来源生成；只有这些来源后来全部未通过
  命题复核且换源耗尽时，才允许进入第四档；
- 用户取消生成；
- 模型网关、输出 schema、语言、结构、锚点或其他质量检查失败；
- 未知程序异常。

触发矩阵如下：

| 必须越界 | 剩余可信来源 | 获取结果 | 行为 |
| --- | --- | --- | --- |
| 否 | 任意 | 任意 | 不允许第四档，沿用论文内质量门 |
| 是 | 有 | 部分或全部检索失败 | 使用剩余来源正常生成 |
| 是 | 无 | 所有计划检索失败/不可调度 | 第四档 |
| 是 | 无 | 检索完成但筛选后为空 | 第四档 |
| 是 | 无 | 来源复核全部失败且换源耗尽 | 丢弃旧正文并以第四档重新生成 |
| 是 | 任意 | 用户取消 | 取消，不生成第四档 |
| 是 | 任意 | 非检索类程序或模型错误 | 失败，不生成第四档 |

## 8. 生成流程

### 8.1 正常三档

前三档继续使用现有论文证据规划、外部来源获取、句级引用和证据复核。模式由最终通过校验
的引用集合计算并写入节点，模型不能直接决定最终模式。

### 8.2 AI 理解档

进入第四档后，生成器创建明确的 `ai_interpretation` 策略输入：

1. 保留用户请求、目标语言和理解主题；
2. 不向正文生成 prompt 提供论文 evidence quote、论文证据摘要、外部来源正文或引用 ID；
3. 不把父节点摘要作为证据注入，只可保留定位主题所需的标题和用户原始问题；
4. 明确要求输出概念分析、推理、假设和可能性，而非事实归因；
5. `paperEvidence`、`externalKnowledge`、`externalSources` 和句级引用均为空；
6. 不生成论文图片推荐、证据型图表、来源锚点或其他暗示文献支持的派生产物；
7. `withinPaperClosure=false`，节点和全部正文句均标记为 `ai_interpretation`。

第四档授权来自编排器传入的受控策略值，不来自模型 JSON。模型返回空证据但没有该授权时，
仍触发现有“缺少论文内证据或外部来源”错误。

## 9. 第四档质量门

第四档跳过需要真实来源才能成立的证据支持复核，但不跳过整体质量门。必须检查：

- `supportMode`、`withinPaperClosure` 和空引用集合一致；
- `summarySentences` 仍完整覆盖正文；
- 每个正文句显式为 `ai_interpretation`；
- 不包含 URL、引用编号、伪造书目或可点击来源；
- 不使用“论文表明”“研究证明”“外部资料显示”等来源性归因；
- 不虚构精确实验数字、统计结论、日期或命名研究发现；
- 假设性示例必须明确表达为假设，不能伪装为观测事实；
- 语言、结构、术语顺序和输出 schema 仍有效；
- 生成审计包含合法的外部来源不可用原因。

可确定判断使用结构化字段和确定性检查。需要语义判断的来源归因与经验事实伪装进入受限的
AI 理解审阅和修复循环。修复耗尽后仍失败，不得继续降低标准或写入节点。

## 10. 界面设计

### 10.1 四档标签

正文元信息区显示一个持久来源标签：

- `paper`：`论文内支持`
- `paper_and_external`：`论文 + 外部支持`
- `external_only`：`仅外部支持`
- `ai_interpretation`：`AI 独立理解`

标签是来源状态，不显示模型、provider、检索实现或开发状态。

### 10.2 背景与边界状态

支持模式使用独立根类。论文内模式保留当前纸张底色；论文与外部共同支持使用克制的浅绿色；
仅外部支持保留当前浅米色；AI 理解使用明显不同的浅红色背景。颜色只承担辅助区分，标签和
声明承担主要语义。

`near_boundary` 仍显示现有边界提示。它与支持模式同时存在时，支持模式决定正文背景，边界
状态只决定边界提示，不覆盖第四档背景。

第四档建议使用接近 `#fff3f1` 的浅红背景、低饱和红色边线和满足可读对比度的深红文字。
不使用渐变、强警报色或大面积阴影。

### 10.3 固定声明

第四档在正文标题之前渲染由本地代码提供的固定声明，使用 Fluent 2 图标并提供可访问名称：

> **无文献依据：AI 独立理解**
>
> 本段必须超出论文范围，但外部检索未获得可信来源。以下正文没有论文内或外部文献依据，
> 仅代表 AI 的独立理解，请勿视为论文结论或事实依据。

声明不依赖模型生成，不能被正文内容、语言修复或流式输出覆盖。第四档不渲染论文和外部来源
角标。选择第四档正文继续提问时，可以把选中文字作为用户问题上下文，但其 evidence ID 和
external source ID 必须保持为空，不能升级为证据。

## 11. 数据流

```text
用户请求
  -> 解释计划判断是否必须越出论文闭包
      -> 否：现有论文内生成与证据硬门
      -> 是：复用既有可信来源 / 执行三路检索
          -> 有可信来源：正常生成与来源复核
              -> 复核通过：paper_and_external / external_only
              -> 全部失效：定向换源
                  -> 有替代来源：重新执行正常生成
                  -> 无替代来源：ai_interpretation 重新生成
          -> 全部失败或无可信结果：ai_interpretation 生成
              -> AI 理解质量门通过：持久化节点与审计
              -> 质量门失败：生成失败
```

## 12. 预计代码边界

主要改动保持在桌面 feature 和 controller 编排边界：

- `thinReading.types.ts`：支持模式、句级模式和外部检索兜底审计契约；
- `thinReadingProjection.ts`：冻结、旧数据推导和节点持久化；
- `thinReadingAgent.ts`：第四档 prompt/解析策略和条件化质量门；
- `generateAssistantAnswer.ts`：外部检索结果联合、受控触发和重新生成编排；
- `ThinReadingTab.tsx`：来源标签、第四档固定声明和根状态类；
- `thinReading.css`：四档背景、声明和响应式样式；
- `src/tests/` 中相应的生成、Agent、投影和界面测试。

`ThinReadingTab` 只消费节点状态并渲染，不决定是否允许第四档。跨步骤触发与恢复继续留在
assistant/controller 编排，保持 `layout -> controllers -> features -> shared types / clients`
依赖方向。

## 13. 测试策略

实施严格遵循 red-green-refactor：先新增失败测试并确认失败原因与目标行为一致，再写最小实现。

### 13.1 状态与投影

- 四种证据组合得到正确节点和句级模式；
- 新节点显式持久化模式；
- 旧节点按引用推导前三档；
- 旧节点空引用绝不推导为第四档；
- 模式与引用不一致时拒绝写入。

### 13.2 获取与编排

- 三路检索全部失败且无既有来源时进入第四档；
- 检索完成但可信来源为空时进入第四档；
- 来源复核全部失败且定向换源为空时重新生成第四档正文；
- 部分检索失败但仍有可信来源时继续正常来源生成；
- 有既有可信来源时复用，不进入第四档；
- `AbortError` 继续取消；
- 论文内普通证据不足、模型失败和解析失败不进入第四档。

### 13.3 Agent 与质量门

- 只有编排器授权的第四档允许空论文和外部引用；
- 普通模式的空引用继续失败；
- 第四档每句均标记为 AI 理解且正文覆盖率为 100%；
- 第四档出现引用、来源归因或精确经验数据时修复或失败；
- 第四档不携带论文图片、证据锚点或来源型派生产物；
- 审计缺失或原因非法时拒绝持久化。

### 13.4 界面

- 四档显示正确来源标签和根状态类；
- 第四档显示固定声明、独立背景类和可访问名称；
- 第四档不显示论文或外部来源角标；
- 移动端声明文字不溢出或覆盖正文；
- `near_boundary` 与第四档同时出现时，第四档背景保持生效。
- 在桌面和移动视口检查截图，确认第四档背景、声明和正文均非空且没有重叠。

### 13.5 验证命令

至少运行受影响的定向测试、完整桌面测试和桌面构建：

```bash
cd products/liteasy/apps/desktop
npm test -- --run src/tests/generateAssistantAnswer.test.ts
npm test -- --run src/tests/thinReadingAgent.test.ts
npm test -- --run src/tests/thinReadingTab.test.tsx
npm test
npm run build
```

若仓库测试脚本不支持上述定向参数，实施计划应使用当前 Vitest 配置认可的等价命令。
界面实现完成后还应使用项目现有浏览器测试基础设施进行桌面和移动视口截图检查；若当前薄读
测试夹具无法驱动该状态，实施计划应增加最小的确定性 fixture，而不是依赖人工修改运行数据。

## 14. 验收标准

1. 用户明确要求越出论文闭包且三路检索全部失败时，薄读不再因无外部来源立即失败。
2. 用户明确要求越出论文闭包且检索没有可信结果时，能够生成第四档正文。
3. 第四档始终显示独立浅红背景、固定声明和 `AI 独立理解` 标签。
4. 第四档正文和句子没有论文或外部引用，且不能声称受到论文或研究支持。
5. 普通论文内证据不足以及其他生成错误仍按现有质量门失败。
6. 前三档根据最终有效证据准确区分，现有可追溯来源行为不退化。
7. 旧文档继续可读，历史空证据不会获得第四档语义。
8. 受影响测试和桌面构建通过，且不覆盖工作区中无关的用户修改。

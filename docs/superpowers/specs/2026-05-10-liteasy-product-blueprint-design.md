# Liteasy 完整产品蓝图与分阶段落地设计

## 1. 文档目的

本文档用于将当前的《Liteasy 功能与 UI 设计文档》收敛为一份可落地的产品与技术设计方案，覆盖：

- 产品目标与范围收敛
- 系统分层与核心模块边界
- 桌面端、云端、Agent、多模态与后台治理的整体架构
- AI 对话控制软件设置与双模型审计机制
- 分阶段交付路线、工程实施建议与主要风险

本文档面向首发形态的长期蓝图设计，而不是单一 MVP 设计。系统将按全景架构设计、按阶段逐步开放能力。

## 2. 已确认前提

### 2.1 产品与商业前提

- 首发形态：桌面优先
- 首批核心付费用户：个人科研用户
- 产品路线：完整产品蓝图 + 分阶段落地路线
- 蓝图策略：按全景式方案 A 设计，但必须分阶段交付

### 2.2 数据与画像前提

- 用户画像策略：中间路线
- 首发阶段只采集产品内行为和用户主动填写信息
- 外部数据接入（如微信、飞书）仅预留授权接口与扩展位，不进入首发主链路

### 2.3 模型能力前提

- 技术路线：混合
- 大模型文本、多模态生成优先使用第三方 API
- 检索、缓存、任务编排、权限和同步能力优先本地或自建

## 3. 产品定位

Liteasy 是一款桌面优先的 AI 驱动科研文献学习工作台，核心目标不是成为通用聊天工具，而是让用户围绕“导入文献、建立工作区、选中文献、提问、深度解析、生成学习产物、沉淀个人知识”的完整闭环持续使用。

Liteasy 的差异化不在于“会回答问题”，而在于：

- 回答必须能定位回论文原文
- AI 助手可以通过对话控制软件内功能与设置
- 用户可以把单篇或多篇论文加工成多模态学习产物
- 软件会基于用户画像和行为偏好优化解释粒度与输出形式
- 系统从一开始就具备扩展到组织协作与平台治理的边界

## 4. 产品范围收敛

### 4.1 首发主链路

Liteasy 首发必须优先保证以下主链路可用且顺滑：

1. 导入文献
2. 建立工作区
3. 选中文献并锁定分析对象
4. 通过 AI 助手进行问答、解释与控制
5. 生成结构化学习产物
6. 沉淀到个人知识、历史会话与画像

### 4.2 现有方案的主要改进建议

#### 建议 1：从“功能清单”收敛为“主链路产品”

当前方案功能覆盖过大，容易导致首版研发目标发散。建议以首发主链路为硬约束，其他功能围绕主链路服务，而不是并列推进。

#### 建议 2：AI 交互模式保留，技术实现统一

右栏保留“名词解释 / 命令 / 问答”三种模式作为用户心智，但技术实现不按三个独立系统构建，而按统一会话入口加任务路由实现：

- 检索解释型任务
- 控制执行型任务
- 深度分析型任务

#### 建议 3：用户画像先做可服务业务的最小闭环

首发阶段优先实现：

- 基础画像：学段、方向、偏好语言、解释深度
- 行为画像：阅读领域、使用频率、偏好输出模态
- 任务画像：更偏爱树形展开、思维导图、PPT 或问答式

暂不把“学术人格分类”和外部应用抓取作为首发主卖点。

#### 建议 4：多模态生成按优先级分层

首发建议优先：

- P0：问答式解析、树形展开、思维导图、PPT
- P1：流程图、数据可视化、苏格拉底问答、费曼学习法
- P2：播客、视频讲解、过程动图

## 6. 技术路线总览

Liteasy 采用“桌面端重交互 + 本地轻计算/轻存储 + 云端任务与同步中台 + 外部模型 API 为主、自建检索与编排为辅”的混合架构。

该路线的核心理由：

- 本地文件、工作区、桌面交互、权限控制天然适合桌面端
- 账号、同步、组织、任务监控、治理天然适合云端
- 多模态生成与推荐任务具有明显异步性
- 学术产品必须兼顾可追溯性、隐私控制与使用成本

## 7. 技术选型建议

### 7.1 桌面客户端

- 推荐：Tauri 2 + React + TypeScript
- 不推荐首发自定义原生 UI

选择原因：

- 相比 Electron 更轻
- Rust sidecar 适合文件系统、索引与本地能力
- React 适合复杂工作台与插件挂载

### 7.2 桌面本地能力层

- 推荐语言：Rust

承担能力：

- 文件系统访问
- SQLite 管理
- PDF 处理与 OCR 编排
- 本地全文索引
- 向量缓存
- 本地日志与权限控制

### 7.3 云端业务服务

- 推荐：NestJS + TypeScript

承担能力：

- 账户与认证
- 订阅与配额
- 同步服务
- 组织服务
- 推荐服务
- 后台服务
- Agent 编排 API

### 7.4 异步任务系统

- 推荐：Redis + BullMQ

承担能力：

- 文献解析任务
- 联网推荐任务
- PPT / 导图 / 视频生成任务
- 双模型复核任务

### 7.5 数据存储与检索

- 云端主数据库：PostgreSQL
- 本地数据库：SQLite
- 向量检索：pgvector 起步
- 本地全文检索：SQLite FTS 或 Tantivy
- 对象存储：S3 兼容对象存储

### 7.6 模型接入

必须建设统一模型网关，统一封装：

- 文本大模型
- Embedding
- Rerank
- OCR
- TTS
- ASR
- 图像生成

所有模型供应商接入都必须经过模型网关，不允许散落到业务代码中。

## 11. 关键任务流

统一任务模式：

`用户动作 -> Assistant / Workspace 触发 -> Agent Runtime 组装上下文 -> 同步回答或异步派单 -> 结果回写会话 / 标签页 / 缓存区`

### 11.1 文献导入链路

1. 用户导入本地 PDF 或打开云端目录
2. 桌面端记录文件元信息
3. Local Knowledge Engine 执行 PDF 解析、OCR、切块、索引建立
4. 如开启云同步，则上传原文与元数据
5. 文献出现在工作区树中，可被勾选分析

### 11.2 问答链路

1. 用户在右栏提出问题
2. Agent Runtime 拉取工作区、勾选文献、对话历史与画像偏好
3. 检索相关 chunk 并构造引用上下文
4. 主模型生成回答
5. 审计模型进行可信度评分与纠偏
6. 文本回填到右栏，引用定位绑定到消息
7. 如需图示或导图，则自动创建异步任务

### 11.3 命令链路

1. 用户输入如“关闭联网推荐”“开启用户画像”“生成思维导图”
2. Runtime 进行意图识别
3. 系统将自然语言映射为内部 command schema
4. 执行器调用相应模块
5. 返回结构化执行结果或可恢复错误提示

### 11.4 多模态生成链路

1. 用户指定单篇或多篇文献生成 PPT、导图或其他产物
2. Runtime 构造结构化大纲
3. 创建 Task
4. Worker 异步执行生成
5. 产物写入对象存储
6. Artifact 元数据入库
7. 客户端收到推送后在中栏打开新标签页

### 11.5 联网推荐链路

1. 用户触发“查找/推荐相关文献”命令，或问答链路需要外部补充
2. Recommendation Service 调用外部检索源
3. 系统进行去重、标准化、打分、关联映射
4. 推荐结果回写左栏缓存区
5. 用户可拖拽到收藏区或文献库

## 12. AI 对话控制软件设置设计

Liteasy 可以通过与 AI 助手对话控制软件设置，但必须采用结构化执行模型，不能把自然语言直接映射为任意本地操作。

### 12.1 控制链路

`用户自然语言 -> 意图识别 -> 命令结构化 -> 权限校验 -> 执行设置变更 -> 返回结果`

例如用户输入“关闭联网推荐”，系统内部应转换为：

```json
{
  "intent": "update_setting",
  "target": "network.recommendation.enabled",
  "value": false
}
```

### 12.2 必须具备的约束

#### 白名单 schema

只允许修改系统已注册的设置项，不允许执行未知目标。

#### 权限校验

按照设置类型区分：

- 本地设置
- 云端账号设置
- 文件系统相关设置
- 组织相关设置

#### 二次确认

以下高风险动作必须要求用户确认：

- 清空用户画像
- 删除文献或目录
- 关闭同步
- 清除缓存
- 修改高权限组织配置

### 12.3 工程建议

- 所有可对话控制的设置项统一注册到 `settings registry`
- 所有命令执行结果统一返回结构化 payload
- 失败信息必须可解释，例如“权限不足”“需先开启画像功能”

## 13. 双模型生成与审计评分设计

Liteasy 可以采用“一个模型生成、一个模型审计评分”的双模型机制，尤其适合学术问答和深度解析场景。

### 13.1 标准链路

`检索上下文 -> 主模型生成答案 -> 审计模型复核 -> 输出可信度与问题点 -> 必要时返工`

### 13.2 审计模型的审查范围

- 是否真正回答了用户问题
- 是否引用了正确论文片段
- 是否存在幻觉或过度推断
- 是否适合当前用户画像的理解水平
- 是否遗漏关键局限性或前提条件

### 13.3 结构化输出要求

审计结果不能只返回一个分数，必须结构化输出：

```json
{
  "score": 0.82,
  "verdict": "pass_with_warning",
  "issues": [
    "结论 2 缺少原文定位",
    "对方法局限性的描述依据不足"
  ],
  "suggested_revision": "补充第 4 页实验设置段落引用"
}
```

### 13.4 使用策略

- 短命令类：不走双模型
- 普通问答：可选轻量审计
- 深度文献分析：必须走双模型
- 多模态生成前的大纲：必须走双模型

### 13.5 前端展示建议

用户侧可以展示：

- 可信度分数
- 是否经过复核
- 风险提示
- 对应引用定位

## 14. 安全、隐私与合规边界

### 14.1 用户画像

- 默认关闭或显式可控
- 支持查看、清空、导出
- 不默认抓取外部应用数据
- 外部数据接口单独授权、单独审计

### 14.2 本地权限

- 本地文件访问采用最小权限原则
- 所有命令执行都必须经过白名单控制
- 不允许模型自由生成系统级操作命令

### 14.3 云端治理

- 审计日志记录关键操作
- 配额与成本监控纳入后台
- 高风险任务支持人工观察与封禁

### Phase 0：原型与底座

目标：

## 16. 团队与实施建议

建议至少按以下研发职责拆分：

- 桌面前端：工作台 UI、标签页、右栏交互
- 桌面 Rust 能力层：文件、索引、缓存、权限
- 云端业务服务：账户、同步、组织、后台
- Agent / 检索 / 多模态服务：任务编排、推荐、双模型、产物生成
- QA / 测试支持：关键链路自动化验证

## 17. 主要工程风险

### 风险 1：首版范围失控

控制方式：

- 以首发主链路做范围门禁
- 所有功能都归入阶段路线

### 风险 2：多模态链路过早过重

控制方式：

- 严格按 P0 / P1 / P2 产物分层推进

### 风险 3：AI 命令执行越权

控制方式：

- 白名单 schema
- 权限校验
- 二次确认

### 风险 4：双模型成本与延迟过高

控制方式：

- 仅在高价值链路启用强审计
- 审计模型可采用轻量模型

### 风险 5：画像与隐私争议

控制方式：

- 首发只做产品内画像
- 外部数据接入单独授权并灰度开放

## 18. 成功标准

首阶段成功不应只看功能数量，而应看以下指标：

- 用户能否顺畅完成文献导入到学习产物生成的闭环
- 回答是否稳定引用论文原文
- 命令式交互是否能稳定控制核心设置
- 多模态产物是否真正帮助理解，而不是演示性质
- 用户是否愿意持续把论文学习放在 Liteasy 中完成

## 19. 结论

Liteasy 最合理的落地方式不是把全部能力一次做满，而是从第一天按平台级架构设计，再按阶段逐步开放能力。首发应围绕个人科研用户的高频学习闭环，建立桌面工作台、Agent 运行时、文献解析与可追溯问答、多模态生成、基础画像与云同步能力。在此基础上，再扩展到组织协作、后台治理和插件生态。

在该方案下：

- AI 助手可以通过对话控制软件内功能与设置
- 可以实现一个模型生成、另一个模型审计评分
- 可以兼顾桌面交互体验、学术可追溯性、云端扩展性与长期平台化空间

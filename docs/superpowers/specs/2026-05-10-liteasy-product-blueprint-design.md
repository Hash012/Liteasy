# Liteasy 完整产品蓝图与分阶段落地设计

## 1. 文档目的

本文档用于将当前的《Liteasy 功能与 UI 设计文档》收敛为一份可落地的产品与技术设计方案，覆盖：

- 产品目标与范围收敛
- 系统分层与核心模块边界
- 桌面端、云端、Agent、多模态与后台治理的整体架构
- AI 对话控制软件能力与双模型审计机制
- 分阶段交付路线、工程实施建议与主要风险

本文档面向首发形态的长期蓝图设计，而不是单一 MVP 设计。系统将按全景架构设计、按阶段逐步开放能力。

## 2. 已确认前提

### 2.1 产品与商业前提

- 首发形态：桌面优先
- 首批核心付费用户：个人科研用户
- 产品路线：完整产品蓝图 + 分阶段落地路线
- 蓝图策略：按全景式方案 A 设计，但必须分阶段交付

### 2.2 数据与画像前提

- 用户画像策略：中间路线
- 首发阶段只采集产品内行为和用户主动填写信息
- 外部数据接入（如微信、飞书）仅预留授权接口与扩展位，不进入首发主链路

### 2.3 模型能力前提

- 技术路线：混合
- 大模型文本、多模态生成优先使用第三方 API
- 检索、缓存、任务编排、权限和同步能力优先本地或自建

## 3. 产品定位

Liteasy 是一款桌面优先的科研 agent 工作台，核心目标不是成为通用聊天工具，而是让用户围绕“建立工作区、勾选并锁定文献、形成选中文献集、导入、按模态分析、提问、生成学习产物、沉淀个人知识”的完整闭环持续使用。

Liteasy 的差异化不在于“会回答问题”，而在于：

- 回答必须能定位回论文原文
- AI 助手可以通过对话控制软件内功能与设置
- 用户可以把单篇或多篇论文加工成多模态学习产物
- 软件会基于用户画像和行为偏好优化解释粒度与输出形式
- 系统从一开始就具备扩展到组织协作与平台治理的边界

从工程上看，Liteasy 至少应分为三层：

- 用户交互层：桌面 UI、工作区、阅读器、对话入口、组织门户与结果展示
- Agent 工作流层：意图识别、上下文装配、skill 调度、生成、审计、回填
- 安全执行边界：只有已注册的 action 才能真正修改软件状态

术语约定：

- 工作区：左栏文献库页面当前可见的目录视图，以母目录及其子目录为边界
- 选中文献集：用户在当前工作区中勾选并锁定、准备交给 AI 的文件集合，基本单位是单个文件
- 导入：把选中文献集送入 AI 知识引擎，完成解析、切块、索引等预处理
- 分析：在已导入的选中文献集上，按某个指定模态启动主工作流

## 4. 产品范围收敛

### 4.1 首发主链路

Liteasy 首发必须优先保证以下主链路可用且顺滑：

1. 打开或建立工作区
2. 勾选文献并锁定，形成选中文献集
3. 将选中文献集导入 AI 知识引擎
4. 通过模态按钮指定模态并启动分析
5. 通过 AI 助手进行问答、解释与控制
6. 生成结构化学习产物
7. 沉淀到个人知识、历史会话与画像

### 4.2 现有方案的主要改进建议

#### 建议 1：从“功能清单”收敛为“主链路产品”

当前方案功能覆盖过大，容易导致首版研发目标发散。建议以首发主链路为硬约束，其他功能围绕主链路服务，而不是并列推进。

#### 建议 2：AI 交互模式保留，技术实现统一

右栏保留“名词解释 / 命令 / 问答”三种模式作为用户心智，但技术实现不按三个独立系统构建，而按统一会话入口加任务路由实现：

- 检索解释型任务
- 控制执行型任务
- 深度分析型任务

#### 建议 3：用户画像先做可服务业务的最小闭环

首发阶段优先实现：

- 基础画像：学段、方向、偏好语言、解释深度
- 行为画像：阅读领域、使用频率、偏好输出模态
- 任务画像：更偏爱树形展开、思维导图、PPT 或问答式

暂不把“学术人格分类”和外部应用抓取作为首发主卖点。

#### 建议 4：多模态生成按优先级分层

首发建议优先：

- P0：问答式解析、树形展开、思维导图、PPT
- P1：流程图、数据可视化、苏格拉底问答、费曼学习法
- P2：播客、视频讲解、过程动图

## 6. 技术路线总览

Liteasy 采用“桌面端重交互 + 本地轻计算/轻存储 + 云端任务与同步中台 + 外部模型 API 为主、自建检索与编排为辅”的混合架构。

该路线的核心理由：

- 本地文件、工作区、桌面交互、权限控制天然适合桌面端
- 账号、同步、组织、任务监控、治理天然适合云端
- 多模态生成与推荐任务具有明显异步性
- 学术产品必须兼顾可追溯性、隐私控制与使用成本

## 7. 技术选型建议

### 7.1 桌面客户端

- 推荐：Tauri 2 + React + TypeScript
- 不推荐首发自定义原生 UI

选择原因：

- 相比 Electron 更轻
- Rust sidecar 适合文件系统、索引与本地能力
- React 适合复杂工作台与插件挂载

### 7.2 桌面本地能力层

- 推荐语言：Rust

承担能力：

- 文件系统访问
- SQLite 管理
- PDF 处理与 OCR 编排
- 本地全文索引
- 向量缓存
- 本地日志与权限控制

### 7.3 云端业务服务

- 推荐：NestJS + TypeScript

承担能力：

- 账户与认证
- 订阅与配额
- 同步服务
- 组织服务
- 推荐服务
- 后台服务
- Agent 编排 API

### 7.4 异步任务系统

- 推荐：Redis + BullMQ

承担能力：

- 文献解析任务
- 联网推荐任务
- PPT / 导图 / 视频生成任务
- 双模型复核任务

### 7.5 数据存储与检索

- 云端主数据库：PostgreSQL
- 本地数据库：SQLite
- 向量检索：pgvector 起步
- 本地全文检索：SQLite FTS 或 Tantivy
- 对象存储：S3 兼容对象存储

### 7.6 模型接入

必须建设统一模型网关，统一封装：

- 文本大模型
- Embedding
- Rerank
- OCR
- TTS
- ASR
- 图像生成

所有模型供应商接入都必须经过模型网关，不允许散落到业务代码中。

## 11. 关键任务流

统一任务模式：

`用户动作 -> Assistant / Workspace 触发 -> Agent Runtime 组装上下文 -> 同步回答或异步派单 -> 结果回写会话 / 标签页 / 缓存区`

### 11.1 文献导入链路

1. 用户打开本地目录或云端目录，建立工作区视图
2. 用户在工作区中勾选并锁定文件，形成选中文献集
3. 用户点击中栏模态按钮，若未导入则先触发导入
4. Local Knowledge Engine 对选中文献集执行 PDF 解析、OCR、切块、索引建立
5. 如开启云同步，则上传原文与元数据
6. 导入状态附着在具体文献条目上，导入完成后选中文献集进入可分析状态

### 11.2 问答链路

1. 用户在右栏提出问题
2. Agent Runtime 拉取当前已导入的选中文献集、对话历史与画像偏好
3. 检索相关 chunk 并构造引用上下文
4. 主模型生成回答
5. 审计模型进行可信度评分与纠偏
6. 文本回填到右栏，引用定位绑定到消息
7. 如需图示或导图，则自动创建异步任务

### 11.3 技能控制链路

1. 用户输入如“关闭联网推荐”“开启用户画像”“生成思维导图”
2. Runtime 进行意图识别
3. 系统选择合适的 skill，并构造结构化 skill input
4. 对涉及文献内容的 skill，默认前提是当前选中文献集已导入
5. 如涉及软件状态修改，skill 只能调用已注册的 action
6. 执行器调用相应模块
7. 返回结构化执行结果或可恢复错误提示

### 11.4 多模态生成链路

1. 用户在工作区中勾选并锁定文献，形成选中文献集
2. 用户点击某个固定模态按钮，明确指定本次分析的目标模态
3. 若选中文献集尚未导入，则系统先执行导入
4. Runtime 构造结构化大纲
5. 创建 Task
6. Worker 异步执行生成
7. 产物写入对象存储
8. Artifact 元数据入库
9. 客户端收到推送后在中栏打开新标签页

### 11.5 联网推荐链路

1. 用户触发“查找/推荐相关文献”命令，或问答链路需要外部补充
2. Recommendation Service 调用外部检索源
3. 系统进行去重、标准化、打分、关联映射
4. 推荐结果回写左栏缓存区
5. 用户可拖拽到收藏区或文献库

## 12. AI 对话控制软件能力设计

Liteasy 可以通过与 AI 助手对话控制软件设置与能力，但必须采用结构化执行模型，不能把自然语言直接映射为任意本地操作。

### 12.1 控制链路

`用户自然语言 -> 意图识别 -> skill 选择 -> action 结构化 -> 权限校验 -> 执行设置变更或能力动作 -> 返回结果`

例如用户输入“关闭联网推荐”，系统内部应转换为：

```json
{
  "skill": "settings.adjust",
  "action": "settings.update",
  "target": "network.recommendation.enabled",
  "value": false
}
```

### 12.2 必须具备的约束

#### 注册 action schema

只允许执行系统已注册的 action，不允许执行未知目标。设置修改只是 action 的一种，其他如启动选中文献集导入、打开指定产物标签页、刷新推荐缓存也应走同样的注册机制。

#### 权限校验

按照 action 类型区分：

- 本地设置
- 云端账号设置
- 文件系统相关设置
- 组织相关设置

#### 二次确认

以下高风险动作必须要求用户确认：

- 清空用户画像
- 删除文献或目录
- 关闭同步
- 清除缓存
- 修改高权限组织配置

### 12.3 工程建议

- 统一注册可调用的 `skill registry`
- 统一注册会修改软件状态的 `action registry`
- assistant 的自由文本只能到 skill 层，不能直接到 action 层
- 所有 action 执行结果统一返回结构化 payload
- 失败信息必须可解释，例如“权限不足”“需先开启画像功能”

## 13. 双模型生成与审计评分设计

Liteasy 可以采用“一个模型生成、一个模型审计评分”的双模型机制，尤其适合学术问答和深度解析场景。

### 13.1 标准链路

`检索上下文 -> 主模型生成答案 -> 审计模型复核 -> 输出可信度与问题点 -> 必要时返工`

### 13.2 审计模型的审查范围

- 是否真正回答了用户问题
- 是否引用了正确论文片段
- 是否存在幻觉或过度推断
- 是否适合当前用户画像的理解水平
- 是否遗漏关键局限性或前提条件

### 13.3 结构化输出要求

审计结果不能只返回一个分数，必须结构化输出：

```json
{
  "score": 0.82,
  "verdict": "pass_with_warning",
  "issues": [
    "结论 2 缺少原文定位",
    "对方法局限性的描述依据不足"
  ],
  "suggested_revision": "补充第 4 页实验设置段落引用"
}
```

### 13.4 使用策略

- 短命令类：不走双模型
- 普通问答：可选轻量审计
- 深度文献分析：必须走双模型
- 多模态生成前的大纲：必须走双模型

### 13.5 前端展示建议

用户侧可以展示：

- 可信度分数
- 是否经过复核
- 风险提示
- 对应引用定位

## 14. 安全、隐私与合规边界

### 14.1 用户画像

- 默认关闭或显式可控
- 支持查看、清空、导出
- 不默认抓取外部应用数据
- 外部数据接口单独授权、单独审计

### 14.2 本地权限

- 本地文件访问采用最小权限原则
- 所有会修改软件状态的执行都必须经过注册 action 控制
- 不允许模型自由生成系统级操作命令

### 14.3 云端治理

- 审计日志记录关键操作
- 配额与成本监控纳入后台
- 高风险任务支持人工观察与封禁

## 17. 开发过程中的效果查看与产品检查机制

Liteasy 不能只靠“代码完成度”判断开发效果，必须同时建立用户可感知的检查机制。建议从演示环境、阶段验收、核心指标和人工体验四个层面看开发进展。

### 17.1 你在开发过程中应该看什么

建议固定检查四类结果：

- 功能是否真的能从用户入口走通，而不是只完成接口或页面
- AI 输出是否能引用回原文，而不是只会泛泛作答
- 多模态产物是否可读、可用，而不是仅生成文件
- 设置、权限、任务状态是否可解释，而不是后台默默失败

### 17.2 建议准备的 4 套可检查环境

#### 1. 交互原型环境

用于尽早确认：

- 三栏布局是否顺手
- 右栏模式切换是否符合直觉
- 中栏标签页和多模态展示是否清晰
- 左栏工作区、收藏、推荐区的信息密度是否合理

这个环境不要求 AI 真跑通，但必须尽早给你看交互骨架。

#### 2. 本地开发联调环境

用于确认真实主链路是否可运行：

- 导入 PDF
- 建立工作区
- 勾选并锁定文献
- 发起问答
- 返回引用定位
- 生成思维导图或 PPT

这是你最常看的环境，主要看“能不能从头到尾用一次”。

#### 3. 集成测试环境

用于确认桌面端、云端、模型网关、异步任务是否联通。这个环境要尽量稳定，用于每周验收，而不是开发者随手改坏也没人知道。

#### 4. 预发布验收环境

用于确认接近真实用户状态时的效果，包括：

- 账号和订阅
- 联网推荐
- 同步
- 双模型评分
- 长任务生成

这个环境不追求最新代码，而追求稳定验收。

### 17.3 建议你每周固定检查的产品清单

每周至少走一遍以下用户路径：

1. 导入 1 篇论文，确认能完成解析并出现在工作区
2. 导入 3 到 5 篇同主题论文，确认多文献勾选和锁定正常
3. 提 3 类问题：
   - 名词解释类
   - 文献细节问答类
   - 综合比较类
4. 检查回答是否带原文引用定位
5. 生成 1 个思维导图或树形展开结果，检查结构是否清楚
6. 生成 1 个 PPT，检查是否能真的帮助汇报
7. 用自然语言修改 2 到 3 个设置，检查命令执行是否可控
8. 人为制造 1 次失败场景，检查系统提示是否可理解

### 17.4 每个阶段建议看的核心验收指标

#### Phase 0

重点不是模型效果，而是骨架是否跑通：

- 是否能导入文献
- 是否有三栏工作台
- 是否能发起对话
- 是否有异步任务状态

#### Phase 1

重点看个人用户闭环：

- 从导入到问答是否能在 10 分钟内完整走完
- 回答是否稳定引用原文
- 思维导图 / PPT 是否可用
- 设置类命令是否稳定执行

#### Phase 2

重点看平台化增强：

- 同步是否可靠
- 联网推荐是否有价值
- 双模型评分是否能识别明显问题
- 推荐缓存区是否真的帮助用户管理外部资料

#### Phase 3

重点看组织与治理：

- 组织空间和共享文献库是否权限清晰
- 后台是否能看到任务、配额、异常
- 审计日志是否能追踪关键行为

#### Phase 4

重点看扩展性：

- 高级多模态产物是否稳定
- 插件是否可控
- 外部授权接口是否明确告知用户并可关闭

### 17.5 建议开发团队给你提供的可视化产物

为了让你不是只看口头汇报，建议团队固定产出以下材料：

- 每周一次录屏：展示本周新增链路
- 一份本周可体验清单：明确哪些功能你可以自己点
- 一份问题清单：当前已知缺陷、限制和不稳定点
- 一份阶段验收报告：按主链路逐条说明是否通过

### 17.6 你自己验收时的判断标准

你验收 Liteasy 时，不要只问“功能有没有”，而要问：

- 我能不能不用开发人员解释就自己完成这条链路
- AI 的回答是否真的基于论文，而不是像普通聊天机器人
- 生成出来的导图、PPT、树形展开是否值得我继续使用
- 设置变更和任务失败时，系统是否说得清楚
- 我会不会愿意把下一篇论文继续放到 Liteasy 里学习

### 17.7 建议加到研发流程里的制度

- 每个 Phase 都有固定“产品走查日”，由你按真实用户方式操作
- 每周至少一次“主链路演示”，禁止只演示局部接口
- 每个核心功能必须有“通过标准”和“失败示例”
- AI 能力必须保留可复现样例文献集，避免每次验收都换数据导致判断失真

### 17.8 面向非开发成员的操作手册要求

考虑到团队中可能有人没有软件开发经验，Liteasy 项目必须从早期开始准备一份独立的“操作手册”，用于指导非开发成员启动、体验和检查产品。该手册不应写成研发说明，而应写成可直接照做的步骤。

操作手册建议固定包含以下内容：

#### 1. 必备工具清单

每个环境都要明确写出：

- 需要安装什么
- 安装地址或下载方式
- 安装完成后怎么确认已安装成功

例如应明确说明：

- 桌面客户端安装包或启动程序在哪里
- 测试账号和密码在哪里领取
- 测试用论文样例包放在哪里
- 哪个链接是测试环境后台
- 哪个链接是日志或任务状态页面

#### 2. 启动步骤

每个环境都必须提供“从零开始”的运行步骤，例如：

1. 打开桌面客户端
2. 登录测试账号
3. 打开指定测试工作区
4. 导入样例论文
5. 等待解析完成
6. 进入右栏发起提问

如果某一步需要命令行，也必须写清楚：

- 在哪里打开终端
- 输入哪一条命令
- 正常情况下会看到什么结果
- 异常时先检查什么

#### 3. 可视化检查点

操作手册必须告诉非开发成员“看到什么才算正常”，例如：

- 论文导入后应该出现在左栏哪个位置
- 解析中、解析成功、解析失败分别是什么状态
- 生成思维导图后中栏会出现什么标签页
- 设置修改成功后界面哪里会反馈
- AI 回答中的引用定位应该怎么看

#### 4. 问题反馈模板

手册应附带统一反馈模板，要求非开发成员反馈时至少包含：

- 使用的环境
- 操作步骤
- 实际结果
- 预期结果
- 截图或录屏
- 是否可稳定复现

## 18. 主要工程风险

### 风险 1：首版范围失控

控制方式：

- 以首发主链路做范围门禁
- 所有功能都归入阶段路线

### 风险 2：多模态链路过早过重

控制方式：

- 严格按 P0 / P1 / P2 产物分层推进

### 风险 3：AI 命令执行越权

控制方式：

- skill registry 与 action registry 分层
- 权限校验
- 二次确认

### 风险 4：双模型成本与延迟过高

控制方式：

- 仅在高价值链路启用强审计
- 审计模型可采用轻量模型

### 风险 5：画像与隐私争议

控制方式：

- 首发只做产品内画像
- 外部数据接入单独授权并灰度开放

## 19. 成功标准

首阶段成功不应只看功能数量，而应看以下指标：

- 用户能否顺畅完成文献导入到学习产物生成的闭环
- 回答是否稳定引用论文原文
- 命令式交互是否能稳定控制核心设置
- 多模态产物是否真正帮助理解，而不是演示性质
- 用户是否愿意持续把论文学习放在 Liteasy 中完成

## 20. 结论

Liteasy 最合理的落地方式不是把全部能力一次做满，而是从第一天按平台级架构设计，再按阶段逐步开放能力。首发应围绕个人科研用户的高频学习闭环，建立桌面工作台、Agent 运行时、文献解析与可追溯问答、多模态生成、基础画像与云同步能力。在此基础上，再扩展到组织协作、后台治理和插件生态。

在该方案下：

- AI 助手可以通过对话控制软件内功能与设置
- 可以实现一个模型生成、另一个模型审计评分
- 可以兼顾桌面交互体验、学术可追溯性、云端扩展性与长期平台化空间

# Agent 长程 PDF 工作流：目标、现状与分支交接

更新时间：2026-09-08（Asia/Shanghai）

## 1. 当前希望完成的事情

当前工作的核心目的不是单纯让应用“能够打开 PDF”，而是建立一条可观察、可复现、可审计的真实 Agent 长程工作流，用它判断 Liteasy 当前是否具备以下能力：

1. 对真实论文进行完整解析，而不是依赖演示文本或 mock 业务结果。
2. 让 Agent 基于整篇论文执行薄读拆解、证据检索、多阶段生成、质量复核和必要的修复循环。
3. 在 Vite 界面中实时看到 Agent 的任务阶段、思考拆解、失败位置和最终产物，而不只看到一个等待动画。
4. 支持在消息框通过 `@论文` 临时加入本轮上下文；该行为应比“修改并重新锁定文献集”更适合随手补充材料。
5. 检查长上下文是否被错误截断，薄读 Markdown 是否过度膨胀，以及可视化产物是否保留完整的证据绑定和原始结构数据。
6. 最终形成两种互补的测试入口：
   - Vite GUI：观察真实用户操作、流式状态和渲染结果。
   - CLI/非 GUI 核心执行：跳过浏览器交互，重复运行并保存完整模型请求、响应、证据和质量门结果。

## 2. 当前采用的实现路径

目前优先完成了 Vite GUI 路径，同时用一个可选的 live evaluation 测试建立了非 GUI 核心执行雏形。正式、可独立分发的 CLI 尚未完成。

测试论文为 *Larimar: Large Language Models with Episodic Memory Control*：

- 文件：`development/test-data/file-workflow-test/larimar-episodic-memory.pdf`
- 页数：18

- Vite 开发路由：`/file-workflow-test/larimar-episodic-memory.pdf`

文件已从桌面端 `public/` 目录移动到稳定测试数据目录。Vite 仅在开发服务器中通过中间件暴露该文件，生产构建不会把论文复制到 `dist`。

在 `file-workflow-test` 分支打开 `http://localhost:1420/` 时，应用会自动注册并打开该论文；使用 `?plain-app` 可以绕过此分支专用夹具。

### 2.2 `@论文` 的上下文语义

普通问答中的 `@论文` 已改为本轮临时附件：

- 发送前等待被引用 PDF 完成解析。
- 通过 `paper` attachment 把论文 ID 送入 Agent 请求作用域。
- 不改变工作区当前的锁定状态。
- 已有锁定文献集时，实际作用域是“锁定集 + 本轮 `@` 论文”的去重并集。
- 重试、重新生成和排队消息保留原来的 `@` 上下文。

生成薄读等产物需要稳定作用域，因此 `/生成薄读 @论文` 在真正启动任务时仍会固定该次产物的论文集合。这与普通问答的临时附件语义并不冲突。

### 2.3 右栏与 Agent 过程展示

此前 Vite 入口会继承浏览器持久化的 Dock 状态。如果用户曾折叠右栏、关闭 Agent 标签或把 Agent 拖到下栏，就会出现“论文已打开但右栏不存在”的情况。

分支专用预览现在会在挂载时：

- 将 `Liteasy Chat` 移回右栏并激活。
- 展开右栏。
- 把异常的三栏比例恢复为 `24 / 52 / 24`。
- 强制开启 Agent diagnostic 展示，使薄读的规划、证据检索、根节点生成、质量校验和修复阶段不会因未登录账户能力而被隐藏。

自动化测试已经覆盖“右栏折叠、Agent 在下栏、右栏宽度异常”的持久化场景。实际浏览器外观仍需人工强制刷新后确认。

### 2.4 Markdown 和原始数据

一次成功薄读生成的旧版 Markdown 达到约 53 KiB，主要原因是同一批完整证据在多个节点和全局证据索引中重复出现。

当前导出逻辑已经调整为：

- 人类可读 Markdown 中单条证据引用最多保留 600 个字符。
- 跨薄读节点按 evidence ID 去重。
- V2 薄读不再重复附加全局证据索引。
- Markdown 中标记“完整证据见原始产物 JSON”。
- 原始 JSON 不执行上述截断，继续保留完整证据、语义对象和可视化证据绑定。
- 可视化 Markdown 只导出可读摘要和语义信息，不泄漏执行脚本、renderer/provider 内部字段或原始图片 URL。

## 3. 已完成的真实运行与验证

### 3.1 PDF 和薄读运行

真实 PDF 通过产品使用的提取器得到：

- 18 页页面数据。
- 70 个检索文本块。

使用本地 dev-cloud 连接 DeepSeek 连续运行三次薄读：

| 运行 | 结果 | 关键状态 |
| --- | --- | --- |
| 1 | 失败 | 三次修复后，摘要句的证据覆盖仍为 0%。 |
| 2 | 成功 | 5 次模型调用；409 个中文摘要字符；9 个证据区段；质量门首轮通过。 |
| 3 | 失败 | 10 次模型调用后，首页方向审计的逐项 verdict 自相矛盾。 |

这个小样本的成功率是 `1/3`。文件读取、全文提取、长程模型调用和质量门链路已经可运行，但模型在严格结构约束下的重复稳定性尚未达标，不能描述为“薄读已经稳定可用”。

成功运行认为纯文本已经足够清晰，因此可视化决策为 `omit / plain_text_sufficient`。未登录的本地开发会话又无法取得账户可视化能力，所以目前没有完成“针对这篇论文生成真实可视化并回放其全程原始数据”的端到端验收。

### 3.2 本地运行材料

以下运行物位于被 `.gitignore` 忽略的 `tmp/`，不会随分支推送：

- `tmp/file-workflow-live-run/result.md`：第 2 次成功运行的 Markdown，生成于证据压缩修改之前。
- `tmp/file-workflow-live-run/failure.json`：第 3 次失败运行的全文提取数据、输入、10 次模型请求/响应和最终错误，约 835 KiB。

当前没有保留第 2 次成功运行的完整 `result.json`。后续评测工具应按 run ID 或时间戳创建独立目录，避免多次运行覆盖成功样本，并应在写盘前剔除凭据和敏感请求头。

### 3.3 自动化验证

- PDF 注册测试验证了 SHA-256、18 页和可提取正文。
- 直接 `@`、锁定集并集、消息重试和薄读命令作用域测试通过。
- Markdown、GFM、数学公式、代码块、Mermaid 和安全渲染测试通过。
- 结构化薄读结果展示和可视化导出压缩测试通过。
- 一轮受影响范围测试：95 项全部通过。
- 右栏修复后的回归测试：24 项全部通过。
- 桌面生产构建通过；149 个生产资源检查通过；测试 PDF 未进入 `dist`。

全量高并发测试尚未全绿：2069 项中 2053 项通过、5 项跳过、11 项失败。失败主要表现为重型渲染和集成测试的 5–15 秒超时；部分单进程复跑可以通过，另有旧文案断言和 mock planner 超时可以稳定复现。该结果需要作为基线测试债务处理，不能用受影响范围测试替代全量发布验收。

服务器中的 Playwright Chromium 缺少 `libnspr4.so`，因此还没有浏览器自动截图证据。当前 UI 结论来自组件测试、构建检查和人工预览入口，最终视觉验收仍需在可运行 Chromium 的环境或人工浏览器中完成。

## 5. 当前必须注意的状态

1. **分支用途**：`file-workflow-test` 包含明确的分支专用临时代码，不应原样进入 `main`。若要产品化，应把测试夹具开关、诊断权限和真实文件注册改造成正式的开发工具边界。
2. **Node.js**：仓库要求 Node.js 20+。当前服务器默认 PATH 曾解析到 Node.js 18，运行时需要把 `/opt/node-v20.12.2-linux-x64/bin` 放到 PATH 前部。
3. **dev-cloud 边界**：`development/dev-cloud` 是本地真实开发 API，不代表生产服务已经验收，也不得加入演示账号或 mock 业务结果。
4. **模型稳定性**：真实薄读仅在三次运行中成功一次。需要把失败类型、repair 次数、token/上下文长度和各阶段耗时纳入可重复评测。
5. **可视化未闭环**：确定性 schema、renderer 和导出测试通过，不代表这篇论文的真实模型可视化已经生成和人工验收。
6. **原始数据留存**：失败轮轨迹存在，但成功轮完整 JSON 缺失；`tmp/` 又不会推送。下一步必须建立脱敏、分 run、可归档的评测产物目录。
7. **UI 人工验收**：右栏恢复和 diagnostics 已有自动化覆盖，但仍等待用户在 `http://localhost:1420/` 强制刷新后确认布局、滚动、阶段展开和最终结果显示。
8. **全量测试债务**：当前全量测试结果不是绿色发布门。合并任何实验分支前，需要在资源稳定的 Node.js 20 环境处理或重新基线化超时用例。

## 6. 建议的下一步

按优先级建议继续：

1. 人工走通一次 `/生成薄读 @Larimar`，录制右栏阶段变化并核对最终薄读节点。
2. 把 live evaluation 从单个可选 Vitest 用例提升为正式 CLI：支持重复次数、run ID、模型/参数快照、逐调用 JSONL、耗时与 token 统计、脱敏和非零退出码。
3. 固定一组真实论文金标问题，对上下文覆盖、证据召回、摘要支持率、质量门修复率和重复成功率做回归统计。
4. 在具备账户可视化能力的会话中强制选择一个确有结构增益的论文节点，完成可视化生成、原始语义数据、渲染结果和 Markdown 压缩的端到端验收。
5. 将成功运行完整 JSON、失败轨迹和截图存入专用、脱敏的评测产物位置；不要继续复用会覆盖旧结果的固定文件名。
6. 最后再决定哪些 Agent/UI 改动可以从 `agent-test-unsafe` 或 `file-workflow-test` 拆成可审计的小 PR 合入主线。
